# Terminal Engines — tmux is the default

**This page is the one authoritative statement of the tmux model.** It used to be spread over
six sections of `CLAUDE.md`, each restating part of it; if you find tmux explained somewhere
else, that copy is the one to delete. Read it before changing anything about engines, session
durability, socket ownership, reattach, or the migration offer.

What a test has to do about tmux is in [testing.md](testing.md) — the short version being that
a test never runs `tmux` itself.

## Both engines coexist

Both engines always coexist: `ptyEngine` is constructed unconditionally, `tmuxEngine` whenever the probe finds a binary. `settings.engine` picks the default **for new sessions only** — it is not a global mode switch, has no `sideEffect`, and never migrates or kills a running session (an older test comment claiming otherwise was wrong). Each shell entry carries its own `engine` instance and a persisted `engineType`, so a mixed set is normal and a restored tab keeps the engine it was born with.

## Why tmux is the default

A node-pty session is a child of `server.js`, so it dies with the process — a crash, an auto-update, or a plain `./restart.sh` took every running agent with it. Under tmux the agent belongs to the tmux server, and three things had to change together for that to actually mean anything:

- **`TmuxEngine.detach(id)`** tears down our attach PTY and leaves the tmux session running. The `detaching` flag it sets is load-bearing: killing the attach PTY fires its `onExit`, and without the flag the daemon's universal engine `'exit'` funnel would tombstone a session whose agent is alive and working. `canDetach` is the capability getter (false on the `Engine` base, so node-pty callers fall through to `kill`). The same commit fixed the map leak on a *real* exit — `TmuxEngine` never deleted its `_sessions` entry, so `has()` stayed true forever and `write()` kept writing into a dead PTY.
- **`shutdown()` detaches instead of killing.** tmux-backed entries are partitioned out before the `killShell` loop and never join the `alive` wait set, so an all-tmux restart also skips the 8s graceful wait. **Only the shutdown path detaches** — an explicit close (`close_session`, the ✕, `DELETE /api/shells/:id`, killall) still goes through `killShell` and really ends the session.
- **The disconnect reaper leaves tmux sessions alone.** `ws.on('close')` used to `killShell(entry, id, 'disconnected')` 30s after the last client left, while the daemon was perfectly healthy. tmux entries now stay **live in `shells`** rather than being detached — simpler, and strictly better: the attach PTY stays open so output produced while you're away still lands in the scrollback buffer and replays when you return (deepsteve never reads tmux's own history), and reconnecting uses the existing "session is still live" path instead of needing a reattach-before-respawn (the WS restore path calls `spawn()`, which would fail against an existing `ds-<id>`).

**Accepted cost:** nothing reclaims a clientless tmux session any more. It runs until closed explicitly. If that growth ever bites, the fix is an idle sweep alongside `pruneClosedSessions()` — not re-arming the reaper.

## Migration off node-pty

`saveSettings()` writes the whole settings object, so every install that has ever saved settings has an explicit `"engine": "node-pty"` on disk and the schema default cannot reach it. Those users get a **one-time offer** instead of a silent flip: `GET /api/engines` exposes `migrationOffer`, the client shows a modal from its startup fetch (so a daemon that booted with no browser simply offers when one appears), and `POST /api/engine-migration {decision}` latches `engineMigrationOffered` either way. The schema `default` is now `'tmux'`, which covers the rest correctly because the block after engine init already downgrades-and-persists when tmux is missing: fresh+tmux → tmux, fresh+no-tmux → node-pty saved, existing → its saved value until it answers. The default can't itself consult `tmuxEngine` (`buildDefaults()` runs ~180 lines earlier); only the `values` thunk is lazy.

**The fallback is visible.** No tmux means a perishable install, so the ⚙ button gets an orange dot (`#settings-btn.engine-fallback`, sharing the one `::after` with the update badge and winning when both apply) and Settings → Terminal prints the `reason` string #619 already produces plus the `tmuxBinary` escape hatch. `applySettings()` re-fetches `/api/engines` — the established idiom there for facts that aren't settings — which is also how a second window drops its copy of the migration modal.

## Spawning, reattaching, and what an exit means

**`spawnSession` degrades instead of throwing, and returns the engine it actually used.** `tmux -V` succeeding at probe time does not prove `new-session` will: the socket path has to fit a Unix socket's `sun_path` (104 bytes on macOS) — since #625 that is `<stateDir()>/tmux.sock`, so a very deep `$HOME` is what blows it rather than `$TMPDIR` + `tmux-<uid>/default`; a home on NFS/SMB where `bind()` is unsupported is a *new* way in (the socket used to always live under `/tmp`); and the tmux server refusing to start lands here too. All three are a real, silent "tmux is installed and completely unusable" state, and the `tmuxSocket` setting is the way out of the first two. The boot log names the socket and its byte count. Because tmux is now the default, that throw would surface from the **raw WS `connection` handler as an uncaught exception and kill the daemon**, taking every other session with it. So a tmux spawn failure now falls back to node-pty for that session, records `tmuxRuntimeFailure`, and lights the same fallback badge (it is a separate field from `tmuxAvailable`, so the dropdown doesn't call an installed tmux "not installed"). **Use the return value** — `engineType` must record what actually spawned, not what was requested; both WS paths additionally catch so a total failure closes one socket instead of the process.

**A missing cwd is caught ABOVE both engines, because the two disagree about it (#632).** Neither surfaces a directory that stopped existing, and they fail in opposite directions. tmux `new-session -c /gone` **succeeds**: tmux hands the start-directory to its server, whose pane child does `chdir(cwd)` → `chdir(find_home())` → `chdir("/")`, so the agent comes up in `$HOME` while `state.json`, `shells.get(id).cwd`, `DEEPSTEVE_CWD` and the tab name all keep naming the path that is gone — and every `git status` the agent runs hits the home directory. node-pty's child fails its own `chdir` and `_exit(1)`s, but only *after* `posix_spawn`/`forkpty` has returned, so `pty.spawn()` throws nothing and the tab merely vanishes via `handleShellGone` → `close-tab`. So `assertSpawnCwd(cwd)` runs as the first statement of `spawnSession`, **above** the tmux→node-pty try/catch described above: inside it, a missing directory would be read as "tmux failed" and degrade to node-pty, which is the silent-vanish half of the same bug. `test/unit/spawn-cwd.test.js` pins that statement order statically, since moving it would break nothing else. Policy and the per-caller surfacing are in [sessions.md](sessions.md#a-sessions-cwd-must-exist-632).

**The reattach entry is spread from `meta`, not hand-listed.** It is the *third* writer of a shell entry (with the WS restore and spawn paths), and it named its fields by hand — so everything added to `serializeShellEntry` since was dropped on reattach and then wiped from state.json by the next save: `forkParent` (the #497 fork-steal guard), `planMode`, `model`/`effort` (#592), `allowedTools` (#612), `scheduled` (#597). Invisible while almost nobody ran tmux; the default path for everyone now. Pinned by `tmux-durability.test.js`.

**Reattach lives in `tmux-reattach.js` and MUST be called after the WebSocket servers exist (#626).** It is invoked at module scope from `server.js`, *below* `wss.on('connection', …)`, because reattaching broadcasts (`recordRecentSession`) and `wss`/`httpsWss` are `const`/`let` — reading them earlier is a temporal dead zone `ReferenceError`, and `typeof` does not save you. That is what shipped from #620 to #626: every session on every boot threw `Cannot access 'wss' before initialization` into the per-session catch, and the swallowed error was logged as `error reattaching session <id>, skipping it`. It stayed hidden for a release because the throw landed on the *last* statement, so sessions did come back — the only symptom was that **`tmux: reattached session …` had never once been printed**, which in turn made it impossible to tell a working reattach from a lucky browser reconnect. Calling it that late is still safe: the whole module body runs to completion before the event loop turns, so no connection is ever served first. The ordering is pinned by a static assertion in `test/unit/tmux-reattach.test.js`, and the log line by `tmux-durability.test.js` + the `linux-service` CI job.

The loop is split into a **critical** phase (reattach → `shells.set` → `wireShellOutput` → watcher → `onExit` → promote → log) and a separately-guarded **best-effort** tail (`recordRecentSession`). A failure in the tail can never be reported as a reattach failure; a failure in the critical phase rolls all the way back — `shells.delete`, restore `savedState[id]`, `detach` (never `destroy`) — so the agent keeps running and the next boot retries, rather than leaving a live-but-deaf entry.

**An attach-PTY death is not an agent death (#626).** The attach PTY is the daemon's *pipe* into the pane, not the agent. `engines/tmux.js` therefore asks `has-session` before propagating an exit: if tmux still has the session, it silently re-attaches (carrying the data/exit callbacks and the pane size forward — `onData`/`onExit` push into whatever entry is current, so a fresh entry would leave the session deaf) and emits `reattach` for the log. Without this, a pipe that broke for its own reasons tombstoned a live agent, and the *next* boot then read that `closed` record and destroyed the still-running tmux session as "the kill didn't take". `detach()` and `destroy()` both suppress it via the `detaching` flag — `destroy()` must set it *before* killing the PTY, since its `kill-session` has not run yet and `has-session` would still say "alive".

The retry budget resets on **elapsed time** (`REATTACH_RESET_MS`), never on output, and that distinction is load-bearing: attaching to a live tmux session always makes tmux repaint the pane, so every retry produces data within milliseconds. A data-based reset therefore reset the budget on every retry — the bound never engaged and the daemon spawned PTYs until `posix_spawnp failed` and stopped serving. Pinned by `engine-default.test.js` (`output alone does NOT clear the budget`).

**Known gap — #607's *recovery* pass under tmux.** Echo-gated Enter itself works under tmux (`prompt-submit.test.js` asserts it there). What does not is the backstop for a *coalesced* text+Enter when the agent has drawn nothing yet: the daemon reads the pane through an attach PTY, an undrawn window is genuinely unreadable, and `confirmPromptSubmitted` correctly ends `unverified` rather than guessing — `[submit] <id> could not read the composer — not retrying Enter`. That is the designed safe outcome (an indeterminate screen must never trigger a re-send), and submission falls back to the pre-#607 *timed* path, which is what shipped for years. The 607B case is therefore pinned to node-pty. Closing it means making the composer readable through tmux's repaint during an undrawn window.

**The attach client must be told it is a UTF-8, truecolor terminal (#624).** tmux is not a transparent pipe: it re-renders the pane for each client using that client's declared capabilities, so an attach client spawned with no flags and no locale silently downgraded every session. Two defects, one cause. (1) tmux sets its client's UTF-8 flag from `-u` or from the first of `LC_ALL`/`LC_CTYPE`/`LANG` containing `UTF-8`; with neither, `tty_check_codeset()` replaces each non-ASCII glyph with **the right number of underscores** — the Claude Code banner rendered as `_______`, `✻ Whisking…` as `_ Whisking_`. (`·` survived, because tmux maps it to an ACS character — a useful control when diagnosing this.) (2) No `RGB` feature was negotiated, so 24-bit SGR was quantized to the 256-colour palette. Neither is visible from an interactive shell, which inherits a locale — **it only reproduces with a service-managed daemon's environment**, and neither the launchd plist nor the systemd unit declares one. `TmuxEngine.attachSpawnArgs()` is now the single definition of an attach spawn (`_attach()` and server.js's `tmux-attach` WS path both call it, having previously been independent copies that drifted): `-u` unconditionally, `-T RGB,256` gated on tmux ≥ 3.2 (an unknown flag exits tmux and kills the tab), and an explicit env. That env is the subtle part — **node-pty's `_sanitizeEnv()` runs only when `opt.env === process.env` by identity**, so passing our own object makes the strip *our* job; `PTY_UNSAFE_ENV` reproduces it, and `TMUX`/`TMUX_PANE` are the ones that matter, since a daemon started from inside a tmux pane would otherwise make every `attach-session` refuse ("sessions should be nested with care"). The pane gets the same locale via `new-session -e`, forced past the "same as the daemon, skip it" diff because a pane inherits the tmux **server's** environment — and the server belongs to whoever started it, possibly the user's own tmux on the shared per-UID socket. `terminalEnv()` (`terminal-env.js`, root so it ships by glob) picks `LC_CTYPE` per platform (`UTF-8` on darwin, `C.UTF-8` elsewhere — **not** `en_US.UTF-8`, which minimal Linux images don't generate) and only when no UTF-8 locale is already set; `childBaseEnv()` layers it in so **both** engines hand the agent the same environment. Deliberately unchanged: pane `TERM` stays `tmux-256color`, and nothing sets `terminal-features` — a per-client `-T` is the narrower assertion and is what we use. (`terminal-overrides` *is* set, but for one unrelated capability and only when the scrollbar setting is on — see below.) The options the daemon *does* set live in one place, `_applySessionOptions()`: `status off`, `mouse on`, `set-clipboard on` — see #650 below — and `terminal-overrides[1]`.

**The mouse is ON, and that is what makes the wheel scroll (#650).** Until #650 the daemon set exactly one option per session, so `mouse` sat at tmux's default `off` and tmux never turned mouse reporting on for its client. That is not a missing nicety — it made scrolling *actively wrong*. xterm.js only translates a wheel into a scroll of its own scrollback when it has scrollback to scroll; the tmux client owns the outer alternate screen, so `buffer.hasScrollback` is permanently false, and with no mouse protocol bound xterm takes its remaining branch and emits `ESC[A` / `ESC[B`. Those are Up and Down: every wheel notch was a keystroke, and scrolling an agent tab walked its prompt history. It was a #620 regression — under node-pty the agent's *own* mouse mode was visible to xterm, so the wheel was reported to the app instead. With `mouse on`, tmux's default root binding decides, and it already encodes the policy we want: `send-keys -M` into a pane that owns the alternate screen or asked for the mouse (Claude, vim, less), `copy-mode -e` into a plain shell pane — real scrollback, exiting by itself at the bottom.

**The browser's scrollbar is `terminal-overrides[1] = *:smcup@:rmcup@` (`browserScrollback`, default on).** tmux's attach client sends smcup (`ESC[?1049h`) when it attaches, so the browser's xterm sits on its **alternate** buffer for the life of the tab — and a terminal on the alternate buffer has no scrollback, so xterm draws no scrollbar. That is the same fact #650 turns on, seen from the other side: #650 stopped the wheel from producing arrow keys, but nothing gave the tab a scroll surface back. Claude Code 2.1.24x closed the last door from the other end — the *pane* owns an alternate screen too (`alternate_on=1`, `history_size=0`), so tmux's own history is empty as well and there is no scrollback **anywhere** in the stack for an agent tab. Deleting smcup/rmcup from the **client's** terminal description keeps it on xterm's normal buffer; lines that scroll off the pane then land in xterm's own scrollback, which is all it needs to draw its native scrollbar. The client's description is the lever, not the pane's: `alternate-screen off` (a window option) fills tmux's *own* history instead and changes nothing in the browser.

Two costs, both measured, neither a reason to leave it off given the alternative is no scrollback at all. The copy is **lossy** — tmux coalesces redraws when output outruns the client, so a fast burst loses a few percent of its lines. And the **wheel still belongs to the pane** whenever the pane asked for the mouse, which Claude does: the wheel scrolls Claude's own view while the scrollbar walks xterm's history. What it does *not* cost, contrary to this hack's reputation, is redraw junk — resizes and reattaches repaint within the visible screen and push nothing into scrollback.

Two things make it safe to re-apply on every attach. It is written **by index**, because `set -as terminal-overrides` *appends*: the same entry would land again on every reattach and the array would grow without bound, while `set -s terminal-overrides[1]` is idempotent. Index 1 because tmux ships exactly one default entry, at `[0]` (`linux*:AX@`), so ours neither displaces it nor is taken down with it. And turning the setting off **unsets** that index rather than merely skipping the write — `terminal-overrides` is a *server* option on a tmux server that outlives the daemon (#620), so an entry a previous boot wrote is still there, and "stop writing it" would have made the setting a one-way door. Gated on tmux ≥ 3.0, which is where array options arrived; below that the unset is a no-op and the set clobbers the whole option. The engine reads the setting through a **getter** called at attach time, not a value captured at construction — it is built once at boot and the setting is live-editable — and an engine that was never handed that getter (`userTmux()`, the legacy-socket migration engine) leaves the option alone entirely, because absent is not the same as false.

The four options live in **`_applySessionOptions()`, called from `_attach()` and not from `spawn()`**, and that placement is the load-bearing part. The tmux server outlives the daemon, so a session created by an older daemon is still running after an upgrade and `spawn()` will never run for it again; `_attach()` is the one funnel every live session passes through — new (spawn), surviving (`reattach()`, `tmux-reattach.js`) and repaired (the #626 silent re-attach). Applying them there is what makes a new option reach an old session on the next restart with no migration step. `mouse` is set with `-t <session>`, the narrowest scope it has, never `-g`. `set-clipboard on` is set with `-s` because it is a **server** option with no narrower scope at all — safe only because #625 made this server ours alone, which is also what the `!this._socket` guard at the top of the method protects: a `socket === null` engine is `userTmux()`, pointed at the user's own tmux, and must never be reconfigured. Each is individually `try{}catch{}`-swallowed so an unknown option on an ancient tmux costs only itself, and `mouse` additionally carries a `_atLeast(2, 1)` gate for clarity rather than for safety. `history-limit` is deliberately left at tmux's default 2000.

Two consequences to know before "fixing" something downstream. A drag over the terminal now belongs to tmux or to the pane's program rather than to the browser, so a copy comes back as **OSC 52** — hence `set-clipboard on`, plus a handler in `public/js/osc-clipboard.js`, since xterm 6.0.0 registers no OSC 52 of its own; and browser-native selection is now the ⌥-drag (macOS) / ⇧-drag escape hatch, which is why `createTerminal()` sets `macOptionClickForcesSelection`. See [frontend.md](frontend.md#terminal-wheel-selection-and-clipboard). Second, the browser now sends SGR mouse reports up the session socket; `isTerminalReport()` correctly reads them as **user input** (nothing in `REPORT_PATTERNS` admits `<`), which is right — a human scrolled. Tests: `test/unit/tmux-spawn-args.test.js` (the argv, and that a bare `reattach()` issues it — the upgrade path), `test/unit/osc-clipboard.test.js`, `test/integration-standalone/tmux-mouse.test.js` (the acceptance test: the mode-set reaches the client, a wheel report lands the pane in copy-mode, and a pane's OSC 52 comes back out). The scrollbar has its own pair: `test/unit/tmux-spawn-args.test.js` (the index, the idempotence, the unset-when-off, and that the setting is read per attach) and `test/integration-standalone/tmux-scrollback.test.js` (the acceptance test: no smcup reaches the browser, and a real `@xterm/headless` terminal fed the session stream ends up on its normal buffer with more rows than fit on screen — the exact condition xterm gates its scrollbar on).

**The pane command is an ARGV, and that is what carries the login flag (#630).** #624's rule — the two engines must hand the agent the same *environment* — has an argv twin, and it was broken from #621 until #630: agent sessions under tmux ran a **non-login** shell, so `~/.zprofile` was never sourced and `/opt/homebrew/bin` (where `brew shellenv` puts it, and which the service PATH omits) never reached an agent's `PATH`. `gh` was `command not found` in every agent tab under the default engine; scheduled tasks surfaced it most, because nobody is watching an unattended run. The mechanism is tmux's one-vs-many rule: **one** `shell-command` argument is an sh(1) command line, which tmux runs through `default-shell -c`, while **two or more** are exec'd directly with no shell in between (tmux(1); the multi-arg form landed in tmux 2.0, 2015 — older than the `-e` support this engine already gates at 3.2, so no version gate). #621 handed tmux the inner command as one string to stop a login shell nesting inside tmux's own; it removed the nesting and the `-l` together. `spawn()` now pushes `[cmd, ...args]` as separate argv elements, so the pane runs exactly one shell, it is the one `resolveLoginShell()` picked, and the argv is byte-for-byte what node-pty is given. Three consequences. (1) `shellQuote()` is gone — there is no shell string to quote — and a **string** `shellCommand` now throws, so the mode that lost the flag is unrepresentable rather than merely discouraged. (2) `-l`/`-c` following the shell path are pane arguments, not tmux flags: tmux bundles OpenBSD's getopt (it needs `optreset`, which glibc lacks) and imports none from libc, so parsing is non-permuting and stops at `cmd`. **No `--` separator** — it is undocumented in tmux(1), so a tmux that did not special-case it would pass `--` to `execvp` as argv[0]. (3) Only **new** sessions pick this up: an existing pane keeps the environment it was born with straight through a restart, which is what #620 bought — so the user-facing instruction is "reopen the tab", not "restart deepsteve". Note also that a login shell *rewrites* PATH rather than adding to it (Debian's `/etc/profile` assigns `PATH=` outright; macOS's `path_helper` demotes inherited entries), so the daemon's own PATH is no longer a reliable channel to an agent — a consequence for tests, which must put a fixture on PATH via the login profile and not via the daemon's env (`test/helpers/login-profile.js` writes every file the resolved shell might read; the thirteen suites that hardcoded `~/.zprofile` were silently inert on a bash box). One divergence this does *not* close and should not be "fixed" the obvious way: `/api/agents` decides a binary is available with `resolveBinary()` (which searches `FALLBACK_DIRS`), while `spawnSession` spawns the **bare name** and lets the login shell resolve it — substituting the resolved absolute path into the command would bypass the nvm/asdf/mise shims a login shell correctly picks up.

Tests: `test/unit/engine-default.test.js` (detach contract, offer matrix, the #626 false-death matrix — **must not import `engines/node-pty`**; see [testing.md](testing.md#the-bare-unit-ci-job-and-what-it-forbids)), `test/unit/tmux-reattach.test.js` (the startup reattach: the ownership rule against the real function rather than a mirror, wholesale field carry, rollback, and the call-order invariant), `test/unit/tmux-spawn-args.test.js` (the `new-session` *and* `attach-session` argv, plus the attach env), `test/unit/terminal-env.test.js`, `test/integration-standalone/tmux-durability.test.js` (the acceptance test: SIGKILL *and* SIGTERM the daemon, assert the pane pid is unchanged and the work inside it still running), `test/integration-standalone/scheduled-unattended.test.js` (a *running scheduled task* survives a restart with no browser ever attached — #626's hard requirement), `test/integration-standalone/tmux-glyphs.test.js`, `test/integration-standalone/engine-migration.test.js`, `test/integration-standalone/login-shell.test.js` (#630's acceptance test — the stub agent is reachable **only** via the login profile, with a same-named decoy on the daemon's own PATH so skipping the login shell is a named wrong answer rather than a timeout; both engines, the pair being the parity claim). `test:standalone` runs in **no** CI job, and every Linux tmux path CI does exercise uses `agentType: 'terminal'` — the one arm #630 didn't touch — so the `systemd` job also carries an "An agent pane gets the user's login PATH (#630)" step, the only place the agent argv meets a real tmux under a real service manager.

## Socket ownership — `HOME` isolation IS socket isolation (#625)

Every tmux invocation carries `-S <stateDir()>/tmux.sock` (`paths.js`'s `tmuxSocketPath()`, mirrored by `service.sh`'s `ds_tmux_socket` and compared by a unit test). A daemon with its own `HOME` therefore gets its own tmux server for free, and **no test has to do anything**. `TMUX_TMPDIR` is inert to deepsteve and is **banned under `test/**`** — `test/unit/tmux-sandbox-guard.test.js` fails the build on it, on `kill-server`, and on any tmux exec outside `test/helpers/tmux-sandbox.js`.

Before this, the engine inherited tmux's default per-UID socket, isolation rode on "set `TMUX_TMPDIR`, and remember to `mkdir` it", and a suite's `after()` hook ran `kill-server` through a variable its `before()` assigned late — so an early throw left it undefined, Node dropped the env key, and the reap destroyed every live agent on the machine. Three times in twenty minutes.

**The env var was worse than fragile: inside a tmux pane it does nothing at all.** A tmux client that inherits `TMUX` ignores `TMUX_TMPDIR` and talks to the server named there — and since #620 every deepsteve tab *is* a pane, so an agent running the suite had no isolation whatever, `mkdir` or not. `-S` has no such failure: it beats an inherited `TMUX`, and pointing it somewhere unusable starts a new empty server rather than silently resolving to someone else's. That asymmetry is the whole reason for the change.

Two paths still reach tmux's shared per-UID socket, both explicit and named. `userTmux()` (a `socket: null` engine) backs the "Attach tmux session" menu and the `tmux-attach` tab — sessions deepsteve did not create; our own `ds-*` no longer appear there. And a **one-time migration** at startup: any non-closed `engineType:'tmux'` record missing from our socket but present on `defaultTmuxSocketPath()` gets its old pane ended (`kill-session -t ds-<id>`, by name, ids from our own state.json only) and is tombstoned. Leaving it running was the unsafe option — the record still says "restorable", so the next reconnect would `--resume` the same transcript into a new pane beside the old one. `uninstall.sh` likewise ends our tmux server before deleting the directory holding its socket.

The **ownership rule survives as the second line of defence**: a `ds-*` session absent from our state.json is logged (with the exact `kill-session` command) and left strictly alone; only a session whose own record is a `closed` tombstone gets reclaimed. Consequence by design, unchanged: a genuinely orphaned `ds-*` is never garbage-collected.

Escape hatch: the `tmuxSocket` setting (default `''` = derive). Two real cases — a `$HOME` deep enough to blow the ~104-byte `sun_path` limit, and an NFS/SMB home where `bind()` is unsupported. That second one is *new*: before #625 the socket always lived under `/tmp` and was therefore always local. The boot log names the socket and its byte count so both are diagnosable in one `grep`.

## `pasteText`: a second route into a pane (#656)

`write()` sends bytes down the attach PTY — the stdin of our `tmux attach-session` client. That tty has a kernel input queue holding `MAX_INPUT` (1022 bytes on macOS, measured), so a multi-kilobyte prompt necessarily sits in it partly unread while the client drains it. A blocking master write with a live reader loses nothing, but a `tcsetattr(TCSAFLUSH)` on the slave mid-stream discards **exactly one queue-full**, silently — and two of those is ~2044, which is the shape of the two live deliveries that lost 2026 and 2038 contiguous characters off the head of ~2.4 KB prompts.

`Engine.pasteText(id, text)` is a second, explicit route for a block of text. The base implementation is exactly `write()`, so node-pty and every other engine are unchanged; `TmuxEngine` overrides it with `load-buffer -b ds-<id> -` (text on stdin via `execFileSync`'s `input`) followed by `paste-buffer -b ds-<id> -t <session> -p -r -d`. The text then reaches the pane through the tmux server's own bufferevent, which answers a slow reader by waiting rather than by losing bytes, and the queue that ate the head leaves the path entirely.

Three flags, none of them optional — `test/unit/tmux-paste.test.js` pins the argv because each is silently load-bearing and getting one wrong still mostly "works":

- **`-r`** — do **not** replace linefeeds. `paste-buffer`'s *default* is to turn every LF into a CR (tmux(1): *"any linefeed (LF) characters in the paste buffer are replaced with a separator, by default carriage return"*). Our prompts are multi-line: without `-r`, each newline arrives as Enter and the prompt submits itself a line at a time.
- **`-p`** — insert bracketed-paste markers, but tmux does it only *"if the application has requested bracketed paste mode"*. That is pane state we cannot observe and tmux can, so delegating **fails safe**: a pane without mode 2004 gets exactly the bytes it got before, not a literal `[200~` typed into its composer. (Claude Code 2.1.246 does parse them — its key table maps `[200~` to paste-start and `[201~` to paste-end.)
- **`-d`** — delete the buffer. Explicitly named buffers are **not** subject to `buffer-limit`, so one that outlives its paste is a leak; the `catch` deletes it again for the case where `paste-buffer` itself failed.

Two contracts a caller must respect. It is **not ordered against `write()`** — `write()` is one stream down the client PTY and this goes around it, so the two must not be interleaved for a single logical input; Esc and Enter deliberately stay on `write()`, since Enter arriving as its own stdin read is the whole of #607. And it **falls back to the attach PTY on any failure**: a pane sitting in copy-mode ignores `paste-buffer`, and an unreachable server must not lose the prompt. The one caller today is `submitWithConfirmedEnter`, gated on the agent's `supportsPaste` capability and on `PROMPT_PASTE_MIN_BYTES`; see [sessions.md](sessions.md#getting-a-prompt-into-the-agent).

## tmux is invoked directly, never through a shell (#619)

Every tmux call is `execFileSync(<resolved absolute path>, argv)` — `engines/tmux.js`'s `_exec()`, plus `hasSession()`/`listAllSessions()`, which exist so `GET /api/tmux-sessions` and the WS `tmux-attach` path stop running tmux themselves. It used to be `zsh -l -c 'tmux …'` everywhere, which quietly made the whole engine conditional on **zsh** being installed: on a Linux box with tmux and no zsh the probe threw, `available` was false, `settings.engine` was rewritten back to `node-pty` at startup and the option vanished from Settings — reported as the useless "tmux not available". Resolution now lives in **`tmux-path.js`** (root-level so `restart.sh`'s `cp *.js` and `release.sh`'s `for rootjs in *.js` ship it automatically; `engines/`'s embed list is hand-maintained): a pure-`fs` scan of `$PATH` and then `FALLBACK_DIRS`. **`/opt/homebrew/bin` is in that list because the LaunchAgent plist PATH omits it** (`release.sh`) — that omission is the entire reason a login shell was there, so don't "simplify" the fallback list away. `tmuxBinary` (setting, default `tmux`) is the escape hatch for a nix/asdf/custom-prefix tmux; it applies on restart, since the engine probes once at construction. The unavailable path now names the binary and every dir searched. Two things that were *not* changing then: `shellQuote()` stayed (it quoted the shell-command string **tmux itself** ran via a shell, a different layer) — **#630 deleted it**, because the pane command is now argv and no such string is left to quote; and `#{session_width}`/`#{session_height}` come back empty on modern tmux (3.6) and parse to NaN — pre-existing, same format string as before, and unobserved since the submenu renders only name + attached. Tests: `test/unit/tmux-path.test.js`, which is the coverage the issue says nothing had — the CI unit job runs bare on ubuntu-latest with **no zsh**, making a fake tmux on disk there literally "tmux present, zsh absent". That job also forbids a unit test from importing `engines/node-pty`, which is why `engines/tmux.js` requires it lazily; see [testing.md](testing.md#the-bare-unit-ci-job-and-what-it-forbids).
