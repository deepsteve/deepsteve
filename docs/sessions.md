# Sessions

The life of a session after it is spawned: what survives a restart, how a closed one is
recovered, how a prompt actually reaches the agent, what happens across a laptop sleep, and
what is different about a session that lives in a git worktree.

The engine underneath all of this is in [terminal-engines.md](terminal-engines.md). The short
version that matters here: under tmux the process outlives the daemon, so most of the
persistence machinery below is the node-pty story plus the fallback for a pane that really died.

## What survives a restart

Under tmux this is mostly moot — the session never went anywhere; startup reattaches the live pane. What follows is the node-pty path, and the tmux fallback when a pane really did die.

When daemon restarts:
1. SIGTERM triggers `saveState()` → writes shell IDs + cwds + claudeSessionIds to `state.json`
2. `stateFrozen` flag prevents shell `onExit` handlers from overwriting state.json during shutdown
3. On startup, loads `state.json`
4. When client reconnects with saved ID, spawns `claude --resume <claudeSessionId>` in saved cwd
5. If `--resume` fails (exits within 5s), falls back to `claude -c --fork-session --session-id <newUUID>`

## A session's cwd must exist (#632)

**A spawn whose cwd is gone is refused, never relocated.** `spawnSession` calls `assertSpawnCwd(cwd)` (`paths.js`, next to `expandTilde`) before it touches an engine, and each surface pre-flights with `spawnCwdProblem()` so the message fits: the two WS paths send `{type:'error', code, cwd, message}`, `/api/start-issue` and `/api/start-automation` answer `400`, the MCP tools (`open_terminal`, `run_in_terminal`, `start_issue`) return `isError` telling the agent to pass an explicit `cwd`, and a scheduled task records a failed run row instead of running. Codes: `cwd-missing`, `cwd-not-a-directory`, `cwd-unusable`. A falsy cwd is deliberately allowed through — `serializeShellEntry` writes the field unconditionally, so a record can carry `undefined`, and that has always meant "inherit".

One related trap worth naming, because guarding a path with `existsSync` is the obvious-looking fix and it is how this bug hides: `/api/start-automation` applied its configured repo as `if (meta.repo && fs.existsSync(meta.repo))`, so a repo that had been deleted silently *declined* the override and ran the automation in `$HOME` under its own name. An `existsSync` guard on an override is not a safety check, it is a silent fallback. A configured repo is now applied unconditionally (`expandTilde`d, which also fixes a `~/…` repo that always failed that test) and refused by the check like anything else.

**Validate the *spawn* cwd, never the agent's resolved cwd.** A Claude session with `--worktree` is spawned in the repo root and creates `.claude/worktrees/<name>` itself, so `DEEPSTEVE_CWD` / `getWorktreePath()` legitimately name a directory that does not exist yet (see `sessionEnv`). Checking those instead would refuse every Claude worktree spawn on its first run. Checking inside `spawnSession` gets this right by construction, because that is the value handed to the engine.

**A refused restore keeps its record.** The check sits above the restore branch's `delete savedState[id]`, so the tombstone survives, the row stays in the restore modal, and the conversation comes back if the directory does. `/api/recoverable-sessions` flags each row with `cwdMissing` (stat of `e.cwd` verbatim — the value restore will spawn in, for both worktree shapes; memoized per request). Since #658 the window picker aggregates the flag rather than showing it per row: a window's dead sessions are subtracted from the count it promises and from what `buildSelection` sends, the row says how many were dropped, and a window with nothing left is drawn disabled rather than offering a reopen the server will refuse. The one behavior change to know about: a **non-Claude** worktree session records the worktree path as its own cwd, so after `merge_worktree` or the `prune-worktrees` skill removes it, restore now refuses where it used to produce a `$HOME` shell. Claude worktree sessions are unaffected — their cwd is the repo root.

**Known gap, unchanged:** a *relative* cwd is neither resolved nor rejected. `expandTilde` only expands `~`, and the two engines resolve a relative path against different processes (the daemon's cwd vs the tmux server's). Normalizing to absolute is a separate behavior change with its own blast radius (`meta.repo`, `task.project`, MCP `cwd`).

## Tombstones — a record is never hard-deleted by a runtime path

**Session records are never hard-deleted by a runtime path (#561).** Every close/kill/wipe — killall, `closeSession()`, `DELETE /api/shells/:id`, natural PTY exit, clear-disconnected — writes a `closed: true` tombstone into state.json (keeping `claudeSessionId`, `cwd`, `worktree`, `name`, `windowId`, plus `closedAt`/`closeReason`), so reconnecting with the shell id can always resurrect the conversation via `--resume`. Never write `delete savedState[id]` in a close path; use `tombstoneSession()` (explicit closes) or `handleShellGone()` (engine `onExit` epilogue — also exposed on the MCP mod context). The only sanctioned purges are an explicit `DELETE /api/shells/:id?forget=1` (what the UI ✕ on an already-closed row sends, and what test cleanup uses) and the retention sweep `pruneClosedSessions()` (`closedSessionRetentionDays` setting, default 30 days; never touches non-closed entries). Every state.json write first rotates the previous file to `state.json.bak`, and the loader falls back to the `.bak` when state.json is missing or corrupt — so a full reset requires deleting both files. **A tombstone resurrects on a plain WS reconnect with its shell id — except when the client sends `noRestore=1`** (#596), which only `app.js`'s server-pushed `open-session` handler does: that connect acts on a session the server said exists, so if it died in the meantime the answer must be `gone`, not a resurrection. Every genuine restore path (restore modal, TabSessions reconnect, orphan claim, recents) omits the flag and is unaffected, and a refused connect leaves the tombstone intact.

**`closeReason` is forensic evidence, so a browser echo must not overwrite it (#626).** A server-initiated close (scheduled auto-close, `DELETE /api/shells/:id`, killall) sends the tab a `close-tab`; the browser tears the tab down and sends `close-session` back. That echo used to re-run `tombstoneSession(id, entry, 'user-closed')`, so **every** unattended auto-close was recorded in state.json as though a person had closed it — which is precisely what sent #626's diagnosis down the wrong path for a day. The WS `close-session` branch now returns early when `shells.get(id) !== entry`, mirroring the guard `ws.on('close')` already had. Any new close path must preserve the same rule: the first writer of a close reason wins.

## The restore surface

**The surface** is `GET /api/recoverable-sessions` + `showSessionRestoreModal` (`public/js/session-restore-modal.js`). The endpoint is a superset of `/api/windows` (same `buildWindowsView()` builder — keep them in lockstep): window groups plus the buckets `/api/windows` deliberately omits — `ungrouped` (no windowId, not currently shown in any browser), `closed` (#561 tombstones), and `recents` (ring-buffer lineages absent from state.json, restorable only via the mint-new-id `POST /api/recent-sessions/:key/restore`; everything else restores by plain WS reconnect with the original id, which also consumes the tombstone). Unnamed sessions get a `label` derived from their transcript (`deriveSessionLabel`: the `ai-title` line, else the first user message; first 256KB only, mtime-cached) — derivation lives ONLY in the recoverable endpoint, never in `/api/windows`, which is on every window's startup path. Cross-window coordination broadcasts `restore-claimed` (claimed ids; other open modals drop those rows) — never a blanket dismiss.

**The modal offers windows, not agent sessions (#658).** Two things here are called a "session": the browser window that held seven agent tabs, and each agent inside it. What you lose in a crash is the *window*, so that is the unit the modal trades in — one row per window group, saying how many sessions it holds, when it was last active and which projects it spans, plus **one** row for the whole `ungrouped` bucket (live agents with no windowId are real, but N of them are not N windows). A window is taken whole, and **one at a time**: the rows are a radio group defaulted to the newest row that can still reopen. Pre-checking every offerable row was the original behaviour and it turned one lost window into a tab holding every window the browser had ever had — so a wholly-missing window is both drawn disabled and skipped by the default (the fallthrough lands on the newest *restorable* row), and when a sibling window claims the selected one the default is recomputed rather than leaving Reopen dead. Only `mode: 'archive'` still multi-selects. `buildSelection` emits a `{ windowId, sessions }` group even for a single-session window, because `WindowManager.claimSessions` needs the windowId to clear the donor window's localStorage rows. Sessions whose directory is gone (#632) are subtracted from the count the button promises and from what is actually sent, and the row says how many — a window must not come back two sessions short in silence.

#560 offered the other unit, and it did not survive its own success: 1100 rows on a real install, of which **301 could not be restored at all** (176 terminal tabs with no conversation; 125 Claude sessions whose transcript was never written, so `--resume` dies in ~1s) and **379 were never closed by the user** (agents that exited, `run_in_terminal` scratch tabs the daemon tears down by design, worktrees auto-closed after a merge). The header called all 1100 "recoverable sessions" — that was the size of the retention window, not a count of what could be recovered.

**The closed + recents buckets are opt-in: `?include=closed`.** Building `closed` costs one synchronous `fs.readSync` per unnamed tombstone — ~448 ms on a 1100-row install, on the event loop, stalling every live PTY — and the window picker never draws it. `closedCount` is returned unconditionally because it is free and it is the only thing that tells the client whether asking again is worthwhile; an install whose sole survivors are tombstones would otherwise read as "nothing to restore". One predicate (`isArchived`) feeds both the count and the rows, so they cannot disagree — a unit test in `scheduled-not-recoverable.test.js` pins that.

**The per-session list still exists as the mass-loss surface** (`mode: 'archive'`), which is what #561 added it for. `offerSessionRestore()` reaches it only when a *deliberate* re-entry — the empty state, the ▾ new-tab menu, the command palette — finds no windows and no ungrouped sessions, and it then re-fetches with `include=closed`. It never appears at startup and never appears beside windows, and nothing in it is pre-checked. Close reasons are translated on the way out (`describeCloseReason`): `tmux-pane-exited` and `exited` are exits, not intentional closes, and no raw enum is ever shown. The startup auto-show still fires only when orphaned/ungrouped sessions exist. The modal dismisses only via its explicit buttons — no overlay click, no Escape.

## Getting a prompt into the agent

Two independent problems, both solved in #607: knowing *when* the agent will accept a prompt,
and knowing that the prompt was actually *submitted* rather than left staged in the composer.

**Prompt readiness is LEVEL-triggered, not edge-triggered.** `deliverPromptWhenReady` used to park a queue head on a one-shot `e.onIdleOnce` that `setWaiting` fired only on the `false→true` transition. When the screen classified `'unknown'` at drain time while `e.waitingForInput` was **already true**, that edge had already passed — `reclassifyWaiting` no-ops on `'unknown'` and `setWaiting` early-returns on a no-change — so the callback could never fire and **the prompt was never even typed**. Reachable for the 2nd queued prompt (an inherited `/rc` followed by the issue prompt) and for the async `fetchIssueFromGitHub` path, which arms delivery seconds after the tab has already gone idle; worse, a later `'working'→'waiting'` pass would inject the stale prompt as a surprise. It is now `e.pendingDelivery`, served by `servePendingDelivery()` from inside `reclassifyWaiting` — which already runs on **both** the PTY data path and the 1s waiting sweep, so no new timer is involved. A `PROMPT_READY_DEADLINE_MS` (30s) submits anyway if the screen never becomes decisive, counting **ambiguous time only** (a `'working'` screen pushes the deadline out, so a long turn never gets a prompt shoved into it). `onIdleOnce` is gone; `onCodexReadyOnce` is unaffected because its arm site already checks the level.

**Ink input parsing / confirmed submission.** `shell.write("text\r")` doesn't work for submitting to Claude — Ink only recognizes Enter when `\r` arrives as its **own stdin read**, so `submitToShell()` writes the text and the `\r` separately. The fixed 1s gap that used to separate them was only ever a *proxy* for "Ink consumed the text": under load (many tabs, a cold start, a busy machine) the child can go longer than that without servicing stdin, both writes sit in the tty buffer, one `read()` returns them together, and the prompt ends up **staged in the composer and never sent**. Three things now make submission confirmed rather than assumed:
- **Completeness-gated Enter.** `submitWithConfirmedEnter` writes the text, then waits for `entry.outputSeq` to move (a monotonic PTY-chunk counter — output after our write proves the child read it) *and* for `promptDraftVerdict()` to report `'complete'`, before sending `\r`. Capped (`echoMaxWaitMs`), with a `PROMPT_ECHO_MIN_GAP_MS` floor so a false-positive confirm can never make the gap *shorter* than the old 1s. It used to gate on `readComposerDraft()` merely being non-empty, and #656 is what that cost: one echoed character satisfied it, so **every** delivery fired Enter at the earliest instant the loop allowed — a 4.2 KB prompt and a 2.4 KB prompt both confirming at 455 ms — whether or not the write had finished arriving.
- **Verify and retry.** `confirmPromptSubmitted` polls afterwards and re-sends **`\r` only, never the text** (re-typing would duplicate the prompt if the first Enter merely landed late) when the agent is idle *and* `isPromptStaged()` says our prompt is still in the composer. It bails on a running turn, on any non-ours write to the PTY, and on a screen it can't read — an indeterminate window ends in `unverified`, not a retry. Silence extends the window rather than burning it: a frozen child's last frame predates our typing, so reading it as "not staged" is the exact #607 misread.
- **What the screen can and cannot answer (#656).** `promptDraftVerdict()` is deliberately *not* "does the draft equal what we wrote", and must not become it. `promptScreenView` reads one 40-row viewport of a 120x40 emulator, so a multi-kilobyte draft rendered uncollapsed does not fit; when it overflows, the composer scrolls to the cursor and what is legible is the **end** of the draft, with the head off-screen on a perfectly good delivery. "The head is missing" is therefore ambiguous between *we lost it* and *it scrolled away*, and guessing would clear and re-type healthy prompts. The question it does answer is the one the gate needs: **is the end of our text there yet?** Seeing our head but not our tail is a write still in flight, and after `echoStallMs` the composer is cleared with Esc and the text written again — once. Nothing has been submitted at that point, so a wrong read costs a re-type, not a duplicate prompt. For a collapsed paste, where none of our characters echo at all, the `+N lines` count is the signal, and it is exact rather than a guess: Claude Code builds the label as `cr(e, t) = t === 0 ? '[Pasted text #e]' : '[Pasted text #e +t lines]'` with `t = pr(text) = (text.match(/\r\n|\r|\n/g) || []).length`, so **N is the newline count**, a single-line paste carries no clause at all, and a 38-newline prompt that arrived without its head reads `+8 lines`. Comparison strips whitespace rather than collapsing it, because `readComposerDraft` joins the composer's rows with a space and a soft wrap inside a long word therefore inserts a character that was never in what we wrote.
- **The transcript is the only exact oracle (#656).** Every screen-side check compares the *first* `COMPOSER_MATCH_CHARS`, so a delivery that lost its **head** reads as "not staged" (and is never retried) and a submitted fragment whose head did land reads as "submitted" — and `state === 'working'` short-circuits to `'submitted'` before anything is read at all, which a fragment satisfies because it really does put the agent to work. Two live deliveries lost 2026 and 2038 contiguous characters off the head of ~2.4 KB prompts and were logged as clean. `checkDeliveredPrompt` (server.js) reads what Claude Code recorded — `claudeProjectDir(...)/<claudeSessionId>.jsonl` — and hands it to `prompt-delivery-check.js`, which compares **both ends and the length**, because the loss shows up in three different shapes: a lost head (only a suffix test sees it), a lost tail (only a prefix test sees it), and a hole in the middle (both ends match and only the count gives it away). It runs **detached** — never awaited, never joined to the delivery promise, never holding `promptDelivering` or `inputBlocked` — so its budget is deliberately outside the 60s arithmetic below. It fails silent in every uncertain direction, per the same rule as the verifier: no record yet, an agent whose transcripts we do not understand, a session id that moved, or a record matching neither end all report "don't know". Slash commands are skipped outright — an inherited `/rc` leaves no user record at all, so it would report unconfirmed every time.
- **Large prompts do not go down the attach client's tty (#656).** Above `PROMPT_PASTE_MIN_BYTES` (1024, measured in bytes because the queue counts bytes), a prompt for an agent with `supportsPaste` goes through `engine.pasteText()` instead of `write()`. See [terminal-engines.md](terminal-engines.md#pastetext-a-second-route-into-a-pane-656) for what that does and why. Esc and Enter stay on `write()`: Enter arriving as its own stdin read is the whole of #607.
- **`composer-state.js`** is where "is it still staged" lives, and it must consult **only the composer box** — after a successful submit the prompt text is still on screen as a transcript line, so a whole-screen substring test reports "staged" every time and double-submits every prompt. (`isPromptOnScreen()` is the opposite, deliberately naive, whole-screen check, used only as positive evidence that the agent *received* the prompt.) `❯` is also the selection cursor of permission dialogs and AskUserQuestion menus, and an empty composer still carries a placeholder hint — both are fixtured in `test/unit/fixtures/composer-screens.js`.
- Gated by the `promptSubmitVerify` setting (default on, read live) and scoped to screen-classified agents (claude). `killShell`'s `/exit` deliberately stays on the timed path — it disposes `entry.terminalScreen` and drops the data handler *before* submitting, so echo could never confirm and every shutdown would burn the cap. Hence `confirmEcho` is **opt-in per call**, set only by `drainPromptQueue`.
- Timings are env-overridable (`DEEPSTEVE_SUBMIT_ECHO_*`, `DEEPSTEVE_SUBMIT_VERIFY_*`, `DEEPSTEVE_PROMPT_READY_DEADLINE_MS`) and budgeted **together** to stay under the 60s `inputBlockTimer` / client banner: 30s readiness + 8s echo + 12s verify = 50s. Raising one means re-checking the others (a unit test asserts it, deriving all four numbers from the source). #656 bought the echo phase 3 more seconds to cover its one re-type and paid for them out of `verifyGraceMs` (4000 → 3000); the verify worst case is `verifyGraceMs * (verifyRetries + 2)`. The delivery check's own `DEEPSTEVE_DELIVERED_*` caps are **not** in this budget — nothing waits on them.
- Tests: `test/unit/{composer-state,prompt-submit,prompt-delivery,prompt-delivery-check,tmux-paste}.test.js` and `test/integration-standalone/prompt-submit.test.js`. **The bash stubs every other standalone suite uses cannot see this bug** — bash `read` is line-oriented and the pane is in canonical mode, so text+`\r` always arrives as one line whether or not the daemon split the writes. The repro needs `test/helpers/stubs/fake-claude-tui.js`, a raw-mode node TUI that models Ink's own-read rule and whose `readAfterMs` policy withholds stdin service so coalescing happens **at the file descriptor**, by construction. `DS_KEEP_TMP=1` preserves its stdin/event logs.
- The stub's #656 knobs, and one trap each: `readChunkBytes`/`readGapMs` drain stdin with `fs.readSync()` on a timer, **not** `process.stdin.read(n)` — any stream listener makes libuv hoover the fd into the stream buffer at once, so the bytes leave the kernel queue immediately and the condition under test disappears (the same trap the coalescing case has). `dropFirstBytes`/`dropAfterBytes` discard a contiguous run without echoing it, from the front or after a grace run, which is the only deterministic way to manufacture a queue flush. `pasteMarkers` honours `ESC[200~`/`ESC[201~` across reads that straddle a marker and renders the collapsed placeholder. `transcript` appends each accepted message to the Claude Code transcript at the path the daemon derives — without it the delivery check has no oracle and can only ever say "unconfirmed". **The scratch root is `realpath`'d** because on macOS `os.tmpdir()` is `/var/…` while a child's own cwd resolves to `/private/var/…`, and the two sides would derive different project directories. The last case in that file stops the daemon, so new cases go above it.
**Starting an issue session has one implementation (#642).** `startIssueSession()` in `server.js` owns the whole thing — caller inheritance, worktree, spawn args, `/rc`, prompt delivery, the `open-session` message — and both server entry points are thin wrappers over it: `POST /api/start-issue` adds request parsing, the config-profile resolution and the multi-window pre-flight; MCP `start_issue` adds caller lookup and its result shape. The wand picker is the third caller and does not spawn through it (it creates its own tab over the WS), but it no longer renders the prompt either: it sends `{type:'issue', issue:{…}}` and the server renders. `wandPromptTemplate` therefore has exactly **one** reader, `renderIssuePrompt()` in `issue-prompt.js`, which also owns the tab-name truncation and the `github-issue-<n>` worktree name. Before this there were three copies, and they had drifted six ways: two of them inherited `/rc`, two called `recordRecentSession`, one derived `engineType` from `getDefaultEngine()` instead of `spawnSession`'s return value (so a tmux→node-pty fallback recorded a lie), and the two server paths disagreed about the cwd reported to the browser, the cwd pre-flight, and whether to auto-open a browser. Any new issue-start surface calls `startIssueSession`; a second copy is what the guards in `test/unit/issue-prompt.test.js` exist to catch. End-to-end coverage of all three paths: `test/integration-standalone/start-issue.test.js`.

**Autopilot merges the issue session when the work is done (#643).** It is a **server-side session variable** — `autopilot` on the shell entry, in `serializeShellEntry` beside `planMode`/`scheduled`, so it survives a refresh, a browser close and a daemon restart. It is deliberately **not** a prompt fragment and **not** a queued prompt. Every issue prompt ends — in *both* states — with an instruction to call the `issue_complete` MCP tool when the work is done, appended by `renderIssuePrompt()` after the `{{var}}` substitution; that tool reads `autopilot` off the calling session **at completion time** and answers either "when you complete, run `/deepsteve:merge`" or "stop here, leave the tab for review". Reading the variable that late is the whole design: nothing is queued, so nothing needs cancelling. The alternative — deliver the clause through `deliverPromptWhenReady` when the switch is flipped — has an irreversible ON, because a queued prompt passes through four stages and only the first two can be cancelled (in `e.promptQueue`: splice it out; armed as `e.pendingDelivery`: null it; handed to `setTimeout(submitAndNotify, …)`: the timer handle is never stored; inside `submitToShell().then(…)`: no abort signal and the text is already being typed) — and cancelling in stages 1–2 would also have to unwind `promptDelivering`, `inputBlocked`, `inputBlockTimer` and `loading`/`prefill`, or input stays blocked until the 60s safety timer. None of it matters once the agent has *read* the clause anyway. Three details worth keeping: the instruction lives in `renderIssuePrompt`, **not** in `WAND_DEFAULT_TEMPLATE`, because the settings modal POSTs `wandPromptTemplate` on every save, so any install where the user has ever hit Save has the old default materialized and a token added to the shipped default would silently never appear there; the ON answer names `$deepsteve-merge` for a Codex caller, since the Claude form is a command Codex does not have; and if the `merge` skill is **not enabled** the answer hands over the mechanical steps (`merge_worktree` then `close_session`) instead of naming a command that does not exist — a stuck agent improvises `git push origin <branch>:main`, which is the failure this page warns about below. Three switches write the variable: the picker checkbox, the tab context menu via `POST /api/shells/:id/autopilot`, and the `autopilot` parameter on `POST /api/start-issue` / MCP `start_issue`. **What a session starts with is a remembered preference, the `issueAutopilot` setting (#651).** `startIssueSession` — and the WS `{type:'issue'}` handler, the picker's own path — reads it whenever the caller omits `autopilot`; an explicit boolean still wins, which is why both server entry points now pass the field through raw rather than `!!`-ing an absent one to `false`. It was per-browser `localStorage` when Autopilot shipped, and that was the bug: a key in one browser is not something the server can read, so an issue started by MCP `start_issue`, `/deepsteve:github-issue` or any autonomous agent — the paths most runs take — always came up off no matter what the user last chose. Two surfaces write the setting, the picker checkbox (still remembered even if the picker is then cancelled) and Settings → GitHub → Magic Wand; the tab context menu deliberately does **not**, because "actually, merge this one" is a per-session correction and must not silently redefine every future issue. Unlike `wandPlanMode` beside it, the setting IS broadcast: the picker paints its checkbox synchronously, before its own `/api/settings` fetch resolves, so the value has to already be in the client, and `applySettings()` stays its only writer there — same rule as the per-session value, the browser renders what the server announced and never decides. The server **announces** the accepted value back (`broadcastAutopilot` → `{type:'autopilot', id, autopilot}`) rather than letting each window keep its own copy, and that is not cosmetic: the picker's `{type:'issue'}` reaches the server *after* the `{type:'session'}` message that reports a session's fields, so that message necessarily says `false` on a picker start — and a flip made in one window has to reach the tab strip in the others. The browser never writes the value itself; the context menu renders whatever the last broadcast said. Unlike #627's auto-close this **fails closed** — an agent that never calls `issue_complete` simply doesn't autopilot, and you get a finished worktree tab, i.e. today's behaviour. Every call is logged (`[MCP] issue_complete: …`) because the call *rate* is the only thing that would justify a daemon-side backstop; storing the flag on the entry is what keeps that cheap. Plan mode is untouched: `wandPlanMode` still gates the plan, and autopilot only means "after the plan is accepted and the code is implemented, merge without asking again". **Every start logs the value, where it came from, and which surface asked (#653).** One line per start, from all three paths: `[issue] #N: id=…, source=<http|mcp|ws-issue>, agent=…, engine=…, worktree=…, cwd=…, autopilot=<on|off>(<setting|explicit>)`. `source` is a parameter on `startIssueSession()`, never a heuristic — #642 unified the three implementations and in doing so dropped the MCP tool's own `[MCP] start_issue #N:` line, leaving one line that could have come from anywhere; the picker's `{type:'issue'}` branch does not call `startIssueSession` at all and so logs its own, a moment after that session's `[WS] Creating NEW shell:` line. `explicit` means the caller passed a boolean, `setting` means it was seeded from `issueAutopilot` — the distinction is the point, because "off because the caller said so" and "off because the setting is off" are different bugs. A `, setting=<on|off>` clause is appended **only** when an explicit boolean contradicts the remembered preference, which is the one case worth spotting: MCP `start_issue` exposes `autopilot` as an agent-settable argument, and a model that helpfully fills in `autopilot: false` is otherwise an invisible override of a user preference. `POST /api/shells/:id/autopilot` already logged its flips (`[API] autopilot on for <id>`); the gap was only at start. Tests: `test/unit/issue-complete.test.js`, `test/unit/tab-autopilot-menu.test.js`, and the autopilot cases in `test/integration-standalone/start-issue.test.js`.

**`/rc` inheritance covers server-side spawns (#519).** `maybeInheritRemoteControl` fires not only from the browser WS new-tab/fork path but also from `start_issue`, `open_terminal` (via the MCP context) and — since #642, which merged the issue-start paths — `POST /api/start-issue`, with the caller as parent. Prompts are sequenced by a per-shell FIFO inside `deliverPromptWhenReady` (`e.promptQueue`) — the inherited `/rc` submits first, then the issue/initial prompt waits for the next idle; the loading banner and `prompt-submitted` fire only after the **last** queued prompt lands (since #607, only after that prompt has been *verified*, not merely written). Never arm `e.pendingDelivery` directly for prompt delivery — queue through `deliverPromptWhenReady`. **Whether the parent has it on is read off the parent's rendered screen, not its scrollback** — `sessionHasRemoteControl` asks `TerminalScreen.linesSync()` for the bottom `RC_FOOTER_ROWS` rows and looks for Claude Code's `/rc active` footer there. It used to grep the last 8KB of raw PTY bytes, which is a pile of overlapping repaint frames (the same property that makes `classifyScreenTail` key on spinner *recency* rather than presence): the footer from before the user toggled `/rc` off stayed in that tail until 8KB of fresh output pushed it out, and a tab parked at its prompt emits none — so "on" was sticky for as long as the tab sat there, and a tmux reattach made it permanent by replaying the pane's history into a session that resumed with Remote Control off. Note that Claude Code can now also turn Remote Control on by itself at startup (`remoteControlAtStartup`, user scope, `/config`); deepsteve neither sets nor reads that setting.

## Knowing whether a session is busy

**BEL detection / waiting classifier.** Claude emits `\x07` (BEL) when it reaches its input prompt — its "I need attention" signal. The server tracks `lastBelTime` (and `lastInputTime`, set whenever input is written to the PTY). `waitingForInput` flips true only after ~2s of PTY silence **and** a BEL has fired since the user last submitted (`lastBelTime >= lastInputTime`) — so a long, quiet tool call (bash, slow network) is no longer mis-classified as "waiting" (#500). Sessions that have never emitted a BEL (terminal bell disabled) fall back to the legacy silence-only heuristic. This `waitingForInput` state drives browser notifications, the hash-commands overlay, the overview waiting dot, the Action Required auto-cycle mod, and auto-submission of `initialPrompt`. Since #634 it only **dismisses** the hash-commands overlay on a busy transition — whether `#` may *activate* is decided by a live read of the composer (`public/js/composer-caret.js`), never by this flag, which is true for a composed-but-unsent message by design.

## Shutdown, scrollback, and plain terminal tabs

- **Graceful shutdown**: The shutdown sequence tries `/exit` first (with Ctrl+C interrupt if Claude is busy), waits 8s, then SIGTERM, then 2s more, then SIGKILL. Process group kills (`-pid`) are attempted first for child process cleanup. Under tmux, shutdown *detaches* instead — see [terminal-engines.md](terminal-engines.md).
- **Scrollback buffer**: Each shell keeps a ~100KB circular buffer. On reconnect/restore, the full buffer is replayed to the terminal before any new output, so you see history.
- **Terminal tab persistence on restart** (the **node-pty** story — under tmux, since #620, the process itself survives and startup reattaches the same live pane): Plain terminal tabs (`agentType: 'terminal'`, spawned via `open_terminal` or the `deepsteve:terminal` skill) are persisted in `state.json` the same way Claude sessions are, and are restored on reconnect by re-spawning `zsh -l` in the saved `cwd`. What survives: the tab, its name, and its `cwd`. What does NOT survive: running processes (SIGTERM/SIGKILL during shutdown), the scrollback buffer (in-memory only), and any env set during the session. `--refresh` does not change what's persisted — it only controls whether the browser force-reloads vs. silently reconnects its WebSocket; the server-side restore path is identical.

## Sleep resilience (#563)

macOS sleep freezes the daemon and suspends browser pages at *different* times (DarkWake runs the daemon ~45s while pages stay frozen), which used to reap live sessions ("disconnected") and stall reconnects after every wake. Four cooperating pieces:

- **`sleep-watch.js`** — dependency-free 5s tick; a >20s wall-clock gap between ticks means the daemon was frozen → records `lastWakeAt`. Consumers call `holdoffRemaining(ms)` before treating client silence as absence.
- **Sleep-aware detach reaper** — `armDetachReap()` (server.js) wraps both 30s detach grace timers (terminal + tmux-attach). Note that since #620 a **tmux-backed session never arms it at all**: it stays live with no client, so the sleep problem below simply doesn't arise for the default engine — this matters mainly for node-pty installs and `tmux-attach` tabs now. At fire time it re-arms instead of reaping if the daemon woke within `DETACH_HOLDOFF_MS` (120s) **or** the timer itself fired >10s late — the late check matters because overdue timers run in due-time order after a freeze, so the reaper can otherwise beat sleep-watch's own overdue tick. Net: a session is only reaped after 120 *contiguous daemon-awake* seconds with no client, so a post-wake reconnect always wins. Test overrides: `DEEPSTEVE_DETACH_GRACE_MS` / `DEEPSTEVE_DETACH_HOLDOFF_MS`. The reload-channel heartbeat similarly re-pings instead of terminating on the first missed pong after a wake.
- **`power-assertion.js`** — while any session is open (and `preventSleepWhileActive` is on, the default), the daemon holds `caffeinate -i -w <pid>` so the Mac doesn't idle-sleep out from under live sessions (availability must not depend on a user-managed caffeinate tab). Reconciled by a 5s `sync()` tick rather than hooks at the six `shells.set` sites; `-i` deliberately does **not** block clamshell sleep; macOS only.
- **Client wake watch + liveness probe** — `public/js/wake-watch.js` detects wake (`visibilitychange`, `online`, timer-gap) and two modules react. `server-probe.js` cuts short whatever `/healthz` backoff it is sleeping in and restarts the schedule at `BASE_DELAY_MS` (#665) — a delay measured against the pre-sleep world is worthless, and without this a woken tab sat out the full cap before looking again. `ws-client.js` reacts at the socket level: sockets mid-reconnect retry immediately, and OPEN sockets (which may be dead without an `onclose` after sleep) are probed with `{type:'ping'}` → force-close + reconnect if no traffic arrives in 5s (wall-clock-checked, because throttled background tabs batch timers). **Probes are capability-gated on `pingPong: true` in the server's `session` message** — unknown control messages fall through to the PTY write, so an old server would type the probe JSON into the terminal. A brand-new session attempted while the server is unreachable shows a shared "Server unreachable…" banner with Cancel (`trackPendingCreate`, app.js) — the WS retry loop already queues the create; the banner just makes it visible.

Simulating sleep in tests: `SIGSTOP`/`SIGCONT` the daemon (see `test/integration-standalone/sleep-reap.test.js`).

## Worktree sessions, and merging out of one

Almost every issue-solving session in this repo is a worktree session, so this is the part of
the page most likely to matter to whoever is reading it.

- **Worktrees**: Sessions can be created with a `--worktree <name>` flag that's passed through to Claude Code. The worktree name is persisted in state.json for restore. `./restart.sh` deploys from wherever it lives (`dirname $0`), so the worktree's own `./restart.sh` *does* copy that worktree's contents to `~/.deepsteve/` — useful for testing in-worktree changes without merging. Caveat: it stamps the worktree path into `.install-source.json` (which the in-app auto-update's `git pull` runs against), so for a durable install prefer running `./restart.sh` from the main checkout after merging.
- **A worktree request is a request, not a guarantee — a checkout that can't host one gets the session anyway (#656)**: opening an issue against a repo with **no commits yet** used to kill the tab one to three seconds after it appeared. Claude Code resolves a base branch before creating anything, so `--worktree github-issue-1` against an unborn HEAD prints `Error creating worktree: Failed to resolve base branch "HEAD"` and exits; the daemon saw a healthy spawn, then `[shell-gone] reason=exited up=1s`, tombstoned the session and sent the browser `close-tab`. Nothing on screen or in the log named the cause, so two in a row read as a crash. A directory that is not a repo at all dies identically (`Can only use --worktree in a git repository`). `worktree-support.js` answers both with one `git rev-parse` pair — `--git-dir` first so a non-repo isn't misreported as missing commits, then `--verify --quiet HEAD` — and `usableWorktree(cwd, name, { log })` returns the name or null, logging `[worktree] dropping "<name>" — <reason>`. **Every new-session spawn path routes its worktree through it**: `startIssueSession`, the WS create block (beside the `spawnCwdProblem` guard, above `ensureWorktree`), `open_terminal`/fork in `mods/deepsteve-core`, and the scheduled runner (where `isGitRepo` stays as the cheap pure-fs pre-filter). What lands on the session entry is therefore what the agent was really given, the same reason `spawnSession`'s return value and not the requested engine sets `engineType`. Dropping is the right answer rather than refusing: a worktree isolates changes from the rest of a checkout, and a repo with no commits has nothing to isolate from. `git worktree add` (the path for agents without native `--worktree`) agrees only in the letter — on an unborn HEAD it silently infers `--orphan` and hands back a branch with no shared history that `merge_worktree` could never merge back. Two things that look like they should be short-circuits and are not: an **existing** `.claude/worktrees/<name>` does not rescue an unborn repo (Claude resolves the base branch before it checks), and the **restore** path is deliberately not filtered — a restored session's worktree is part of its identity (`claudeProjectDir` derives the transcript dir from it), so dropping it on resume would point the session at a different conversation. Tests: `test/unit/worktree-support.test.js`, `test/integration-standalone/worktree-unborn-repo.test.js` (whose stub `claude` replicates the real preflight, so it asserts the tab survives rather than merely which flags we chose).
- **Claude Code 2.1.222 isolates worktree sessions, which broke `/deepsteve:merge` (#617)**: 2.1.222 turns on a guard that statically parses every Bash command in a worktree-isolated session and refuses any it can't prove stays inside the worktree — `git -C <shared checkout>` ("redirects git to the shared checkout via -C"), `cd <shared checkout> && git …`, and **any command naming `git` more than once** ("too complex to verify … break it into plain, separate commands"), plus globs, `--bare`, `GIT_DIR`/`env -C` injection and runtime-computed `-C` targets. Version correlation is the proof: ~0 activations across 2.1.201–2.1.221 (2 of 249 on 2.1.220, a gradual rollout), then 6 of 10 sessions on 2.1.222. The strings are in the 2.1.220/221 binaries but the feature is off there, and **there is no config toggle**. This is fatal to the old `skills/merge.md`, whose whole design was "from the worktree, drive the main checkout via `git -C <main_path>`" — it broke at step 1 (the compound state block *and* `git -C "$main_path" branch --show-current`) and step 7 (`git -C <merge_dir> merge`). Splitting commands only clears the "too complex" class; **no Bash rewrite can reach the shared checkout**. The guard applies to the agent's Bash tool, not to the daemon, so the merge moved server-side into the `merge_worktree` MCP tool (`mods/deepsteve-core/merge-worktree.js`, pure logic with an injected git runner; `runGit` in `tools.js` uses `execFileSync('git', argv)` — no shell, so no quoting concerns, no `zsh -l` PATH dependency, and it works on the zsh-less CI unit runner). Merge semantics are unchanged: the same target/merge-dir resolution, the same refuse-on-dirty-target guard, and `--abort` on conflict so the target is left untouched — only `merged` is a success, every other status returns `isError`. **Don't "fix" an agent's guard refusal by having it `git push origin <branch>:main`** — that's the workaround agents improvise, and it moves the remote while leaving the local checkout behind (it left `suburbanmagic` local `main` a commit behind `origin/main`). Note the dirty-target guard assumes the repo gitignores `.claude/` (deepsteve's `.gitignore` has `.claude/*`); a repo that tracks it sees the worktrees dir as untracked and every merge is refused. Tests: `test/unit/merge-worktree.test.js`.
- **A successful merge closes its own session — the daemon does it, not the agent (#627)**: `/deepsteve:merge`'s last step is "call `close_session`", and agents drop it. #609 saw it **30/30** across a batch of worktrees and chose "strengthen the prompt"; that shipped in full and failed again on Opus 5 with all four of #609's angles present in the file. It fails structurally: the natural end of the task is the success summary, the close is work *after* the thing that feels like the end, it sits behind the skill's longest and most variable stretch (conflict → rebase → re-merge), and the failure is silent and costless in the moment — the merge really is complete, only a tab lingers, and the agent is by construction not around to notice. So `merge_worktree` returning `merged` **arms** the close (`armSessionAutoClose` → `session-auto-close.js`, default `mergeAutoCloseMinutes: 2`, `0` = off) and reports `autoCloseAt`/`autoCloseMessage` back; forgetting now degrades the outcome from "open forever" to "closes shortly". Non-negotiable details: **deferred, never inline** — `closeSession` on a busy Claude writes Ctrl+C at once, which would cut off step 8's `gh issue close` and the summary, so the delay is what makes that tail survivable; **worktree callers only** (`caller.worktree`), because `merge_worktree` is a general tool and from the main checkout it is an ordinary merge in a long-lived tab nobody asked to end — that is also what keeps the skill's `in_worktree=false` path untouched; **the safety property is the entry-identity re-check at fire time**, not the cancel hooks — a close/exit/tmux-reattach/`--resume` restore all produce a different entry object, so a cancel site nobody remembers to add later fails *safe*. Cancel hooks exist anyway in `tombstoneSession` (the universal close funnel, beside `pendingOpens.drop`), `killShell` (the detach reaper tears down *without* tombstoning), `submitToShell` (any delivered prompt / `meta_type` / inherited `/rc` means someone is driving the session), the WS keystroke path, and `shutdown()` — that last one matters because shutdown *detaches* tmux sessions (#620) and a close firing in that window would destroy exactly what the detach preserves. It **defers while the screen says `busy`** (and treats a permission dialog as busy, since `classifyScreenTail` folds those into `waiting`) but bounded at 10 × 30s, then **gives up rather than forcing** — a safety net must never be the thing that destroys work, and failing open is just today's behavior. `sleepWatch.deferMsFor(dueAt, …)` is the #563 wake-holdoff rule extracted here for its second caller; it keys on the **due time, not the arm time**, because this one re-arms in a loop and measuring lateness from the original arm would defer forever. Timers are in-memory: a restart inside the window loses the pending close, deliberately (re-arming on boot could close a session the user resumed working in). A user merely *reconnecting* does not cancel — only typing does — so a reload or a post-sleep reconnect can't silently disarm the feature. That last guarantee was not actually true until #635: the browser forwards everything xterm's `onData` emits, including its replies to the capability probes tmux fires at an attaching client, and the WS handler stamped `lastInputTime` and cancelled the pending close for those exactly as for a keystroke. `terminal-input.js` now classifies a payload made up entirely of terminal report sequences (DA1/DA2, DSR, CPR, DECRPM, DCS, OSC) as *not input* — it still reaches the PTY, ahead of the #512 `inputBlocked` drop so tmux's probe is never left unanswered, but it neither stamps `lastInputTime` nor cancels. The default is "input", so an unrecognized sequence leaves a tab open rather than closing one someone was working in; the one accepted collision is a modified F3 (`CSI 1;<mod> R`), byte-identical to a cursor position report. `DEEPSTEVE_MERGE_AUTOCLOSE_MS` overrides the delay for tests. Tests: `test/unit/session-auto-close.test.js`, `test/unit/merge-auto-close.test.js`, `test/unit/terminal-input.test.js` (which drives `@xterm/headless` — the same version the browser loads — and asserts every reply it emits is still recognized), plus `deferMsFor` cases in `test/unit/sleep-watch.test.js`.
