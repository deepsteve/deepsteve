# Scheduled Tasks (locally-queued cron)

Everything about the `scheduled-tasks` mod: how a fire becomes a session, how that session
reports it finished, and the four separate mechanisms that exist because an unattended run has
no browser watching it. Read it before changing anything under `mods/scheduled-tasks/`, and
before assuming a scheduled run behaves like an interactive tab — it does not.

The one rule worth carrying out of here without reading the rest: **a scheduled run is a normal
local agent session**, so it inherits the project's MCP servers, and it can wedge on a
permission prompt exactly like an interactive one can.

The `scheduled-tasks` mod (`mods/scheduled-tasks/`) runs recurring agent tasks **on this machine** on a cron schedule. Unlike Claude Code's cloud `/schedule` (egress-restricted), a scheduled run is just a normal local Claude session, so it gets the project's MCP servers for free — the intended use is recurring MCP-dependent work (e.g. a weekly analytics report). Issue #521.

- **Self-contained tasks**: each task stores its own `prompt` + canonical `project` (git repo root) + 5-field `cron`. Persisted to `~/.deepsteve/scheduled-tasks.json` with the load-on-start / write-through pattern (like `mods/tasks/`). The named groups a task can be scoped by are the shared **contexts** (`~/.deepsteve/contexts.json`, owned by server core since #526) — this mod no longer keeps a `project-groups.json` of its own.
- **Scheduler lives in the mod**: `init(context)` (called by `initMCP`) starts a `setInterval` tick (~30s) using the spawn helpers on the shared `context` object; the run recipe mirrors `/api/start-automation` (`spawnSession` → `shells.set` → `wireShellOutput` → `emitSessionOpen` → `deliverPromptWhenReady` → `deliverToWindow`). No windowId / no forced browser — unattended runs queue their tab via `pendingOpens` and surface when a browser next connects, **if the run is still alive by then** (#596, see below). `server.js`'s only contribution is the `scheduledTasksEnabled` kill-switch setting.
- **Cron is local time**, 5 fields (`min hour dom mon dow`), parsed/matched by `mods/scheduled-tasks/cron.js` (dependency-free; supports `*`, `n`, `a,b`, `a-b`, `*/n`; classic dom/dow OR rule). The UI offers preset builders (hourly/daily/weekly/monthly) plus a raw field.
- **Catch-up once**: on startup (after a ~10s settle), any enabled task whose `nextRun` is in the past runs **once**, then resumes — one catch-up per task regardless of how many occurrences were missed. An **overlap guard** skips firing if the task's previous run's session is still alive **and hasn't self-reported terminal** (`ACTIVE_STATUSES`), so a finished-but-idle tab no longer blocks the next fire.
- **Agent self-reports completion (#525)**: an interactive Claude REPL doesn't exit when it finishes, so completion can't be inferred from the PTY. Instead the scheduled-run prompt is wrapped (only when MCP is wired for the agent — `mcpConfigArgs(...).length > 0`, i.e. claude) with a contract telling the agent it's a scheduled run and to call `scheduled_task_started` when it begins and `scheduled_task_finished` (with `success` + a one-line `summary`) when done. Run status lifecycle: `queued` → `running` → `succeeded`/`failed`, with `ended` as an onExit fallback for a session closed with no self-report. The onExit fallback is **skipped during shutdown** (the session persists + resumes with the same shellId, so it can still self-report after restart). Each run stores `{ startedAt, sessionId, status, endedAt, agentStartedAt, success, summary }` plus, since #565/#592, `{ worktree, worktreeRemoved, model, effort, configDir }` — older rows lack those, so every consumer must treat them as optional. The tool identifies the caller's run via the `?shellId=` in its MCP URL (`findRunByShell`). Legacy `started`/`completed` rows still render in the panel badge.
- **The fire pre-permits its own contract tools (#612)**: deepsteve imposes the self-report contract, so deepsteve makes it callable — `runTask` spawns with `--allowedTools mcp__deepsteve__scheduled_task_started,mcp__deepsteve__scheduled_task_finished`. Before this, whether an unattended run could honor the contract depended on whatever `settings.json` allowlist happened to exist in the target project, and the default path was the worst case: per-run worktree isolation (#565) puts the run in a fresh claude-native worktree with no inherited permissions (`symlinkWorktreeSettings` only covers the *manual* `ensureWorktree` path). A run that blocked on `Do you want to proceed?` never self-reported, so its status stayed `running` forever, the overlap guard skipped **every subsequent fire** of that task, and only `maxRuntimeMinutes` unwedged it an hour later as `timed-out`. Plumbing mirrors #592's model/effort exactly: `allowedToolsFlag` in `AGENT_CONFIGS.claude` → `allowedToolsArgs()` → **both** `getSpawnArgs` and `getResumeArgs` (Claude's `--resume` carries no session flags), with `allowedTools` in `serializeShellEntry` so a restart-resumed run keeps the grant. Names are re-validated at the argv boundary by `validateToolName` (capped at `MAX_ALLOWED_TOOLS`, and the `Bash(git *)` specifier form is deliberately rejected), so a hand-edited `state.json` can't inject arguments. The array is generic and mod-supplied — `CONTRACT_TOOLS` lives in the scheduled-tasks mod, gated on the same `mcpWired` probe that decides whether to inject the contract at all, so core stays agnostic. **Deliberately narrow**: only the two self-report tools. A run can still wedge on a Bash/Edit prompt mid-task and never reach `scheduled_task_finished` — `maxRuntimeMinutes` remains the only backstop for that.
- **Auto-close (per-task, default on)**: `scheduled_task_finished` auto-closes the (unattended) tab unless the task's `keepOpen` (never close) or `keepOpenOnFailure` (keep a failed run open) flags are set — both default `false` and are set at creation via the form checkboxes or the `keep_open`/`keep_open_on_failure` MCP/REST fields. Closing goes through `ctx.closeSession` (acks the tool response before teardown; the now-terminal run status means the onExit fallback won't overwrite it).
- **Background open (#600, `scheduledTasksOpenInBackground`, default on)**: a scheduled fire is unattended, so its `open-session` message carries `background: true` and the tab lands **inactive** — no focus steal, and no `revealTabContext()` yanking the context rail. `runTask(task, reason, { foreground })` computes the flag live off `ctx.settings` (no restart to toggle). Background is the default for schedule fires, catch-up fires and the agent-facing `run_scheduled_task_now` MCP tool; only the panel's own Run-now button (`POST /api/scheduled-tasks/:id/run`) passes `foreground: true`, since the user just asked to see that run. Client side (`initTerminal`, app.js): `if (!restoreActive && (!background || !activeId)) focusTab(id)` — it *does* focus when nothing is active yet, or a lone inactive tab would leave a blank pane behind a hidden empty state; otherwise it gets the unseen-activity badge so it's discoverable. Background opens also skip `progressStart` (the top-of-page progress bar is ambient interruption for work the user didn't start), which is why `progress-bar.js`'s `done()` now early-returns for an id that never called `start()`.
- **Unattended runs must survive having no browser at all (#596)**. Three things used to break in exactly that case, all fixed:
  - **The queued tab outlived the run.** `pendingOpens` is now the self-cleaning queue in `pending-opens.js` (TTL 24h, cap 100, injectable clock — unit-tested standalone). Entries are dropped the moment their target closes (`tombstoneSession()` / `deleteDisplayTab()`, the universal funnels) and re-checked for liveness at flush via `isPendingOpenLive()`. Before this, a run that fired, finished and auto-closed with nobody watching still handed its tombstoned id to the next window, which reconnected with it and got a zombie `claude --resume` tab pointing at a worktree `cleanupWorktree` had already deleted — one per unattended fire. Unknown (mod-defined) message types are never dropped for liveness, only by TTL/cap.
  - **The auto-updater restarted through live work.** `POST /api/request-restart` auto-confirms when zero browsers are connected — which is the unattended case by definition — so the 6-hourly update check killed runs mid-work, leaving `status: 'running'` forever (shutdown skips the run's `onExit`) and leaking the worktree (`sweepLeakedWorktrees` skips ACTIVE runs). `scheduleAutoApply()` now consults `restartBlockers` (registered via the `registerRestartBlocker` ctx hook) and defers in 10-minute steps, up to 6 times, then applies anyway so a wedged run can't starve updates. The mod blocks only for a run that is ACTIVE, has a live shell, and has **no** attached client — a tab someone is watching belongs to them. Deliberately unchanged: an explicit `./restart.sh` is a direct user instruction and still restarts immediately.
  - **A stuck run wedged its task forever.** Nothing reaps an unattended session (`armDetachReap` only arms from a WS `close`, and there was never a socket), so a run parked on a permission prompt kept the overlap guard skipping every future fire. Each task now has `maxRuntimeMinutes` (default 60, `0` = unlimited; settable via the panel, `max_runtime_minutes` on `schedule_task`/`update_scheduled_task`, or the REST body). `enforceRunTimeouts(now)` runs at the head of each tick and closes an over-limit clientless run with status `timed-out` — deliberately **not** an ACTIVE status, so the `onExit` fallback leaves it alone, the worktree sweep reclaims it, and the next fire is unblocked.
  - Related: `browser_eval` / `browser_console` / `screenshot_capture` now return an immediate `isError` when no browser window is connected, instead of broadcasting into the void and timing out after 10s/30s with a misleading "enable the mod" message.
- **Per-run worktree isolation (#565, per-task `isolateWorktree`, default on)**: each fire of a claude task on a git-repo project runs in its own disposable Claude Code worktree `scheduled-<shellId>` (branch `worktree-scheduled-<shellId>`, created by claude's native `--worktree`), so scheduled runs never clobber the main checkout. The prompt contract adds a merge-back clause: commit + merge/push anything worth keeping BEFORE `scheduled_task_finished`. Cleanup runs from the run's `onExit` (after auto-close, manual close of a kept-open tab, or a crash-'ended' run — never during shutdown, so a restart resumes the same worktree via the persisted `entry.worktree`): `cleanupWorktree()` uses `git worktree remove` **without** `--force` (dirty worktree → kept, with its branch) then `git branch -d` (unmerged → branch kept). A daemon restart replaces the mod's onExit with the core restore handler, so `sweepLeakedWorktrees()` (startup + each tick, one attempt per run per process) reclaims terminal-status runs whose tab is gone and whose state.json record is `closed` — checked via `ctx.getSavedSession`, the one initMCP addition. Non-claude agents, non-repo projects, and the homedir fallback all skip isolation and run exactly as before. Run rows record `worktree`/`worktreeRemoved`; the panel shows "(kept)" for preserved worktrees.
- **Per-task model / effort / config profile (#592)**: `model` (alias like `opus`/`haiku`, or a full id like `claude-fable-5`), `effort` (`low|medium|high|xhigh|max`), and `configProfile` (a #537 custom-config-profile **id**) are per-task fields, settable from the panel form and from `schedule_task`/`update_scheduled_task` (`model`, `effort`, `config_profile`) and REST. All three are **claude-only** and default to `null` = inherit Claude Code's own default — which is what every pre-#592 run did, including the silent fallbacks off Opus on usage limits that the issue's 54-run audit surfaced. Plumbing: `AGENT_CONFIGS.claude.modelFlag/effortFlag` → `modelArgs()` → **both** `getSpawnArgs` and `getResumeArgs` (Claude's `--resume` doesn't persist session flags, same reason `--permission-mode` is re-applied), with `model`/`effort` in `serializeShellEntry` so a restart-resumed run keeps them. Values are re-sanitized at the argv boundary by `validateModel`/`validateEffort` (exposed on the mod ctx alongside `resolveConfigDir`), so a hand-edited `scheduled-tasks.json` can't inject arguments. The profile is stored as the **id**, not the resolved dir (a task is a template — editing the profile's directory in Settings should move future runs with it) and resolved per fire via `ctx.resolveConfigDir`; `runTask` was previously the only spawn path in the codebase that never passed `configDir`. Each run row records the **effective** `model`/`effort`/`configDir` (the panel shows them as a `haiku · low` chip in History) — nothing else stores them, and effort appears in no transcript at all. The panel's agent dropdown now comes from `GET /api/agents` instead of a hardcoded list, so profiles appear as a `config:<profileId>` optgroup (the same encoding the main new-tab menu uses; `splitAgentSelection` accepts it on every write path) and `codex` is no longer silently missing.
- **System-level default model / effort (#604)**: `scheduledDefaultModel` (string, default `''`) and `scheduledDefaultEffort` (enum `'' | low…max`, default `''`) are the fallback for any task that pins neither — so a policy like "every automation runs Sonnet + medium" is set once in Settings → Scheduled Tasks instead of per task, and a task an agent creates later via `schedule_task` without `model`/`effort` can't escape it. Resolution per fire in `runTask()`: `cleanModel(task.model) || defaultModel()` (ditto effort), where `defaultModel`/`defaultEffort` read **live** off `ctx.settings` — same as the `scheduledTasksEnabled` gate — so a Settings change applies to already-created tasks on their next fire with no restart. `''` = inherit Claude Code's own default, i.e. pre-#604 behavior. The setting is sanitized twice: `validateModel`/`validateEffort` in the schema entry (so a bad value is *rejected at POST time* with a `warnings` entry rather than silently no-op'ing at fire time) and again via `cleanModel`/`cleanEffort` at the argv boundary — a settings value is no more trusted than a task value. Nothing downstream changes: the run row still records the **effective** values, so history shows the resolved default. `GET /api/scheduled-tasks` also returns `defaults: {model, effort}` so the panel form's "Default" options read `Default (system: sonnet)` instead of a vague "inherit"; both schema entries carry a `sideEffect` that re-broadcasts `scheduled-tasks` so an open panel relabels immediately. Tests: `test/unit/scheduled-default-model-effort.test.js`.
- **A task is never hard-deleted while one of its runs is in flight (#614)**: `task.runs` is the *only* record of the run↔session link (`findRunByShell` matches `run.sessionId` against the caller's `?shellId=`), so splicing a task out mid-run orphaned the live agent it had spawned — `scheduled_task_started`/`scheduled_task_finished` answered "this session is not a scheduled task run", the run was never recorded, the unattended tab never auto-closed (auto-close lives *inside* `scheduled_task_finished`), and `enforceRunTimeouts` + `sweepLeakedWorktrees` lost it too. `deleteTask()` now always unschedules immediately but, when `activeRunOf(task)` is set, keeps the row as a **tombstone** (`deleted: true` + `deletedAt`, `enabled: false`, `nextRun: null`) instead of splicing — the same rule as the #561 session tombstones: a delete may not destroy a record something live still depends on. The split is one accessor: **`liveTasks()`/`findLiveTask()`** for everything that schedules, lists or mutates a schedule (`tick`, `runCatchUp`, `list_scheduled_tasks`, `updateTask`, `run_scheduled_task_now`, `GET /api/scheduled-tasks`, `POST /:id/run`, `knownProjects`), and the **full `tasks`** for everything that reasons about a *run* (`findRunByShell`, `enforceRunTimeouts`, `sweepLeakedWorktrees`, `unattendedRunInFlight`, the run's `onExit` epilogue). A tombstone is invisible everywhere — panel and every `list_scheduled_tasks` scope — and `purgeTombstonedTasks(now)` (in `tick()`, right after `enforceRunTimeouts` so a reaped run releases its row the same pass; saves itself like its sibling, and deliberately **not** called from `runCatchUp` since a restart-resumed run is still ACTIVE) drops it once nothing needs it. Two things pin a tombstone: an ACTIVE run, and **a run holding an unreclaimed worktree** (`run.worktree && !run.worktreeRemoved`) — the tick purges *before* `sweepLeakedWorktrees()` runs in the same interval callback, and after a restart the sweep is the only thing that reclaims a worktree, so purging first would leak the directory permanently. A 7-day `TOMBSTONE_TTL_MS` is the backstop for both (a shell that died so hard nothing moved its status off ACTIVE; a worktree git refuses to remove). The same defect had a second route: `MAX_RUNS` truncation, now `trimRuns()`, which never evicts a row whose `sessionId` is still in `ctx.shells` (a `keepOpen` tab can outlive 20 later fires). `DELETE /api/scheduled-tasks/:id` returns `{deleted, tombstoned, activeSession}` and the panel's delete confirm warns when the newest run is still active. Tests: `test/unit/scheduled-task-tombstone.test.js`.
- **The self-report tools tell the truth about a missing record (#614)**: `noRunResult()` replaced the bare "This session is not a scheduled task run — nothing to mark", which was unfalsifiable — now that a delete keeps the record, reaching it really does mean there is no run, so it names the causes (usually a **resumed or forked conversation replaying the original run's ⏰ header under a new shellId**), says the work itself is unaffected, and hands back `list_scheduled_tasks scope:"all"` + `unschedule_task`. It is *not* `isError` (a no-op notice, not a failure). A run whose schedule was tombstoned still reports normally, with `deletedScheduleNote()` appended. `unschedule_task` returns three distinguishable answers — unscheduled / already unscheduled / no such id — instead of one ambiguous `not found`, so an agent winding its own recurring task down can always get a definitive result using the id from its ⏰ header, whether or not the task appears in a listing. `createTask`/`deleteTask` also log now; before, a deletion left no trace at all and had to be inferred from a *missing* "skipped — previous run still active" line.
- **Panel: inline edit + active-first ordering (#613)**: `Edit` swaps `TaskForm` into the task's **own row slot**, in place of its card — it no longer renders as a sibling above every section, which used to insert ~500px at the top of the panel and throw the row you clicked off-screen. Each row is a keyed `<div data-task-id>` holding either the card or the editor, and that key is load-bearing twice over: it forces a fresh `TaskForm` mount when you go straight from editing one task to another (the old top-level form had no `key`, so it kept the first task's field values while saving to the second's **id**), and `data-task-id` survives the card↔editor swap so the `useLayoutEffect` scroll pin can restore the row's top edge by id after commit. Only `+ New` still renders at the top (`editing` is `{mode:'new'}|{mode:'edit',id}`; it pins `toTop`). `editing` holds an **id, never the task object** — every `scheduled-tasks` broadcast, including a plain scheduler tick, replaces the whole `data.tasks` array, so a held object goes stale; the live task is re-resolved from `sections` each render. Two guards close a dangling editor: the edited task disappearing (deleted here, in another window, or via `unschedule_task`) and any `filter` change. Ordering: the `sections` memo puts **active tasks first** (`isActive` = enabled and not a fired one-shot), as a *partition* so each tier keeps its existing creation order, and sinks whole project sections that have nothing active below the ones that do — otherwise one live task among a hundred paused ones sits at the bottom of the panel. Consequence by design: pausing a task moves its row down on the next broadcast. Client-render only — no REST/MCP/persistence surface changed, and no sort control was added.
- **Cross-project run-history page (#633)**: the panel answers "what does this task do"; it cannot answer "did all my automations run last night, and did any of them quietly stop firing" — it shows one repo at a time, one task's history at a time, in 380px. The history-icon button in the panel header opens a full-screen grid instead: rows are Project (context) → repo → task, columns are that task's runs, newest **leftmost**. Data comes whole from `GET /api/scheduled-tasks/history`, backed by the pure exported `buildRunHistory()`; the route is read-only and therefore shares `list_scheduled_tasks`' carve-out from the fail-closed gate (with the scheduler off you especially want the history *and* the banner saying why nothing fires, which the payload's `enabled` flag drives). The aggregation deliberately shows three things the panel hides, because each is a silently-broken schedule: a task with **no runs at all**, a task whose **repo folder is gone** (`fs.existsSync`, TTL-cached — a missing root is exactly when the volume may be unmounted and a blocking stat is what #553 took off request paths), and a **tombstoned** task whose run is still in flight. It strips `prompt`, and passes `runs` through **unsliced** — `trimRuns()` appends a still-live run *past* `MAX_RUNS`, so slicing to 20 would drop the one run most worth showing; the client sorts by `startedAt`. A repo inside two contexts is listed under both (matching the panel's Show filter), so rows are keyed by `contextId\0root` and any count over them must dedupe by task id. **Skipped fires are recorded nowhere** — the overlap guard, `POST /:id/run` and `run_scheduled_task_now` all return without writing a run row, and adding one to `task.runs` would break `activeRunOf()`, which reads only `runs[0]`; the page says so in its legend rather than implying an empty cell means anything. The page renders in the **top document** (`public/js/scheduled-history.js`), not in the panel's iframe, because mod iframes receive no theme variables at all — so the button reaches it through a new `deepsteve.openScheduledHistory()` bridge hook. Its cells carry a **glyph as well as a color**: `win-95.css` maps `--ds-accent-green-soft` to blue and `--ds-accent-blue` to navy, which would otherwise collapse "succeeded" and "running". "Go to session" is gated on the *client's* tab list, never the server's `shells` — `focusTab`→`switchTo` sets `activeId` unconditionally, so offering it for a session this window lacks would blank the pane. Tests: `test/unit/scheduled-run-history.test.js`, `test/unit/scheduled-history-client.test.js`.
- **Scoping**: `list_scheduled_tasks` defaults to the caller's own project (`sessionPaths(entry).repoRoot`); `scope:'group'` adds sibling repos sharing a project group; `scope:'all'` lists everything. MCP tools: `schedule_task`, `list_scheduled_tasks`, `update_scheduled_task`, `unschedule_task`, `run_scheduled_task_now`, `scheduled_task_started`, `scheduled_task_finished`. The panel (right side) groups tasks by project, with a scope filter, run history (with per-run summary), and group management.
- **`scheduledTasksEnabled` setting** (default on) is the master switch and the server-authoritative on/off — the correct gate because a mod's UI enable/disable is client-side only (per-browser localStorage; never reaches the server). The tick reads it live (settings object is mutated in place), so toggling it in Settings stops/starts the scheduler with no restart. The **same gate is fail-closed at every write/action surface**: the MCP tools `schedule_task`/`update_scheduled_task`/`run_scheduled_task_now` return a clear `isError` "feature turned off" result (`featureOffResult`, `FEATURE_OFF_MSG`) and the matching REST writes (POST create, PUT update, POST `/:id/run`) 403 with the same message — so an agent scheduling into a disabled feature learns why instead of getting a cheerful ack for a task that will never fire. Deliberately **not** gated: `list_scheduled_tasks` (read), `unschedule_task` (cleanup should always work), and `scheduled_task_started`/`scheduled_task_finished` (a run already in flight when the switch flips off must still self-report + clean up). The scheduler timers are `.unref()`'d so `init()` is unit-testable (`test/unit/scheduled-feature-gate.test.js`).
