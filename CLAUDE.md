# deepsteve

DeepSteve is a node server that manages Agent (Claude Code, etc) instances and a Web UI that lets you connect to them in the browser and automate the Agents. Agents running inside of DeepSteve can interact with the DeepSteve system itself, writing custom browser-based UIs as well as interact with each other.

## Development Workflow

### Restart the daemon after making changes:
```bash
./restart.sh            # silent restart — browser reconnects via WebSocket
./restart.sh --refresh  # restart + force browser page reload
```
Use `--refresh` when changes affect anything the browser loads (frontend JS/CSS/HTML, server endpoints, settings). Plain `./restart.sh` only restarts the server process — open browser tabs just silently reconnect their WebSocket, so they keep running old frontend code and won't see new server-side behavior until the page is reloaded.

**`Restart cancelled.` has two causes.** `./restart.sh` first POSTs to `/api/request-restart`, which shows a confirm dialog in the browser. The script prints `Restart cancelled.` and exits if either (a) the user actively dismissed the dialog, or (b) nobody responded within the 60s timeout. Don't assume it was an explicit rejection — the user may have been away from the screen. Ask them to retry or confirm when they're ready rather than silently giving up.

**`--force` skips the in-app modal (#504).** When you can't (or don't want to) confirm in the browser, `--force` moves acceptance to **Claude Code's own permission prompt** for the command instead. It is a deliberate two-step so the user sees the blast radius before accepting:
```bash
./restart.sh --force                       # step 1: prints "Restarting - N active sessions will be interrupted" + the exact confirm command. No restart.
./restart.sh --force --prompt "Restarting - 3 active sessions will be interrupted"   # step 2: restarts after re-checking the text
```
The server owns the wording (`GET /api/restart-prompt`, derived from the live session count); step 2 re-validates the echoed `--prompt` text against the server and aborts if it's stale or forged, so the number you approve is always the real one. The forced path still does a full graceful deploy + restart (it just skips the `/api/request-restart` POST). **Do not allowlist `./restart.sh` (especially the `--force --prompt` form)** — the guarantee that a restart can never happen unilaterally (e.g. by an agent) rests entirely on that command staying behind Claude Code's permission prompt.

**Worktree sessions:** `./restart.sh` deploys from the directory it lives in — it sets `SCRIPT_DIR="$(dirname "$0")"` and copies that directory's `server.js`, `mods/*`, `public/*`, etc. into `~/.deepsteve/`. So running the **worktree's own** `./restart.sh --refresh` *does* deploy that worktree's edits without merging first — handy for testing a change in place. Caveat: it also stamps `.install-source.json` with the worktree path as `sourcePath`, and the in-app auto-update (git-pull) runs against that path. Since worktrees are temporary and sit on feature branches, prefer running `./restart.sh` from the **main repo checkout** for a durable install, and re-run it there after merging.

### View logs:
```bash
tail -f ~/Library/Logs/deepsteve.log
tail -f ~/Library/Logs/deepsteve.error.log
```
Log lines are timestamped in local time (ISO-8601 with offset), and the daemon rotates both files itself at 10MB — the previous generation is kept next to them as `deepsteve.log.1` / `deepsteve.error.log.1` (`logging.js`, #557; works through the launchd-held O_APPEND fd, so no plist change is involved).

### Check if running:
```bash
launchctl list | grep deepsteve
```

### Stop the daemon:
```bash
launchctl unload ~/Library/LaunchAgents/com.deepsteve.plist
```

### Full reinstall:
```bash
~/.deepsteve/uninstall.sh
./release.sh   # generates install.sh from source
./install.sh
```

### Running tests (#562 — the suite can never target the production daemon)

`npm test` (= `test/run-integration.sh`) **auto-provisions a throwaway daemon** when `DEEPSTEVE_URL` is unset: scratch `HOME` (own auth-token/state/settings), random port, `DEEPSTEVE_TEST_MODE=1`, isolated `TMUX_TMPDIR`; torn down on exit. It is safe to run alongside the live daemon. The docker suites set `DEEPSTEVE_URL=http://server:3000` and skip provisioning.

Safety layers (all three must hold — do not weaken any of them):
- `test/helpers/ws-client.js` **requires `DEEPSTEVE_URL`** — importing it without one throws; there is no localhost:3000 fallback (that fallback once let a bare `npm test` wipe every live session).
- Destructive helpers (`httpPost`, `httpDelete`, `WsClient.connect`) first verify the target reports `/api/version.testMode === true`, i.e. was started with `DEEPSTEVE_TEST_MODE=1`. There is no bypass, and none is needed for the public-install suite: since #588 it runs each release's own helpers against that release (see below).
- The server itself refuses `POST /api/shells/killall` (403) unless started in test mode.

`DEEPSTEVE_TEST_MODE=1` (or `--test-mode`) also disables the startup browser auto-open and the auto-update check. Never set it on a real install. Guard regression tests live in `test/unit/ws-client-guard.test.js` (`npm run test:unit`).

**The Public Install suite runs the release's own tests, not main's (#588).** `test/Dockerfile.public` installs via `deepsteve.com/install.sh`, which 302s to `releases/latest/download/install.sh` — so the server under test is always the **last published release**. Main is always ahead of it, so running main's suite against it reddened the daily cron on every post-release feature test until the next release shipped (#579's `context-icon.test.js` asserting `iconImage === ''` against a build where the field didn't exist yet). `.github/workflows/install-integration-tests.yml` now resolves that release tag and `actions/checkout`s **it** before bringing the compose up, so the container under test and the tests exercising it are one commit; a step then asserts the installed `package.json` version equals the checked-out tag, so an `install.sh`-vs-API desync is named rather than surfacing as assertion noise. Three consequences: (1) a new test on main reaches this suite when it *ships*, not when it merges — that is the point, the job's real question is "is the deployed build healthy"; (2) CI uses the **tag's** compose/Dockerfiles/runner, so edits to `test/docker-compose.public.yml` don't affect the cron until the next release, and the workflow file — the one piece that stays current — must keep working against released trees (its contract has been stable since v0.17.0); (3) a local `npm run test:docker:public` from main still has the old skew, so check the release out first (`git checkout $(gh api repos/deepsteve/deepsteve/releases/latest --jq .tag_name)`). **Never add `SKIP_PATTERN` entries for features the released server predates** — that was the failed mitigation #588 removed, and it went stale and read as "we skip tests for features we didn't build." `tmux-engine` is the one legitimate permanent skip (that image installs only zsh + curl). Since #620 made tmux the default, be honest about what that costs: `docker-compose.install.yml` and `docker-compose.public.yml` have no tmux, so they exercise the **node-pty fallback**, not the default engine — which is genuinely worth testing, but it means the main `docker-compose.yml` suite (whose image does install tmux) is the only one covering the default. The durability behavior itself is covered outside Docker, by `test/integration-standalone/tmux-durability.test.js`. `test/unit/public-suite-pin.test.js` guards the workflow's shape.

**Every `test/docker-compose*.yml` declares its own `name:` and publishes no host port (#616).** The three suites are projects `deepsteve-source` / `deepsteve-install` / `deepsteve-public`; without an explicit `name:` compose derives one from the parent directory — `test` for all of them — and since their services are all called `server`/`test`, two suites then share one project: an `up` recreates the sibling's containers and a `down -v` deletes its volumes. And no publish is needed because nothing outside the compose network ever dials the server (the test container uses `DEEPSTEVE_URL=http://server:3000`, the healthcheck curls `localhost:3000` *inside* the server container, and `ws-client.js` has no localhost fallback by #562's design) — while `3000:3000` collides with the developer's own daemon, which is every machine that develops deepsteve. #588 fixed both for the public compose only and #616 found the other two still broken a release later, so `test/unit/compose-projects.test.js` now asserts both properties across a **glob** of `test/docker-compose*.yml`, covering a fourth file on arrival. The `npm run test:*:clean` scripts need no `-p`: they pass `-f <file>` and compose reads the project name out of it. One-time after this change: `docker compose -p test down -v` sweeps the containers/volumes orphaned by the rename.

## Architecture

### Overview

deepsteve runs as a macOS LaunchAgent daemon that serves a web UI for managing multiple Claude Code terminal sessions. Each browser tab gets its own PTY-backed Claude instance.

### Terminal Engines — tmux is the default (#620)

Both engines always coexist: `ptyEngine` is constructed unconditionally, `tmuxEngine` whenever the probe finds a binary. `settings.engine` picks the default **for new sessions only** — it is not a global mode switch, has no `sideEffect`, and never migrates or kills a running session (an older test comment claiming otherwise was wrong). Each shell entry carries its own `engine` instance and a persisted `engineType`, so a mixed set is normal and a restored tab keeps the engine it was born with.

**Why tmux is the default.** A node-pty session is a child of `server.js`, so it dies with the process — a crash, an auto-update, or a plain `./restart.sh` took every running agent with it. Under tmux the agent belongs to the tmux server, and three things had to change together for that to actually mean anything:

- **`TmuxEngine.detach(id)`** tears down our attach PTY and leaves the tmux session running. The `detaching` flag it sets is load-bearing: killing the attach PTY fires its `onExit`, and without the flag the daemon's universal engine `'exit'` funnel would tombstone a session whose agent is alive and working. `canDetach` is the capability getter (false on the `Engine` base, so node-pty callers fall through to `kill`). The same commit fixed the map leak on a *real* exit — `TmuxEngine` never deleted its `_sessions` entry, so `has()` stayed true forever and `write()` kept writing into a dead PTY.
- **`shutdown()` detaches instead of killing.** tmux-backed entries are partitioned out before the `killShell` loop and never join the `alive` wait set, so an all-tmux restart also skips the 8s graceful wait. **Only the shutdown path detaches** — an explicit close (`close_session`, the ✕, `DELETE /api/shells/:id`, killall) still goes through `killShell` and really ends the session.
- **The disconnect reaper leaves tmux sessions alone.** `ws.on('close')` used to `killShell(entry, id, 'disconnected')` 30s after the last client left, while the daemon was perfectly healthy. tmux entries now stay **live in `shells`** rather than being detached — simpler, and strictly better: the attach PTY stays open so output produced while you're away still lands in the scrollback buffer and replays when you return (deepsteve never reads tmux's own history), and reconnecting uses the existing "session is still live" path instead of needing a reattach-before-respawn (the WS restore path calls `spawn()`, which would fail against an existing `ds-<id>`).

**Accepted cost:** nothing reclaims a clientless tmux session any more. It runs until closed explicitly. If that growth ever bites, the fix is an idle sweep alongside `pruneClosedSessions()` — not re-arming the reaper.

**Migration.** `saveSettings()` writes the whole settings object, so every install that has ever saved settings has an explicit `"engine": "node-pty"` on disk and the schema default cannot reach it. Those users get a **one-time offer** instead of a silent flip: `GET /api/engines` exposes `migrationOffer`, the client shows a modal from its startup fetch (so a daemon that booted with no browser simply offers when one appears), and `POST /api/engine-migration {decision}` latches `engineMigrationOffered` either way. The schema `default` is now `'tmux'`, which covers the rest correctly because the block after engine init already downgrades-and-persists when tmux is missing: fresh+tmux → tmux, fresh+no-tmux → node-pty saved, existing → its saved value until it answers. The default can't itself consult `tmuxEngine` (`buildDefaults()` runs ~180 lines earlier); only the `values` thunk is lazy.

**The fallback is visible.** No tmux means a perishable install, so the ⚙ button gets an orange dot (`#settings-btn.engine-fallback`, sharing the one `::after` with the update badge and winning when both apply) and Settings → Terminal prints the `reason` string #619 already produces plus the `tmuxBinary` escape hatch. `applySettings()` re-fetches `/api/engines` — the established idiom there for facts that aren't settings — which is also how a second window drops its copy of the migration modal.

**`spawnSession` degrades instead of throwing, and returns the engine it actually used.** `tmux -V` succeeding at probe time does not prove `new-session` will: the socket path has to fit a Unix socket's `sun_path` (104 bytes on macOS), and `TMUX_TMPDIR` + `tmux-<uid>/default` can blow past it — that is a real, silent "tmux is installed and completely unusable" state, and the tmux server refusing to start lands there too. Because tmux is now the default, that throw would surface from the **raw WS `connection` handler as an uncaught exception and kill the daemon**, taking every other session with it. So a tmux spawn failure now falls back to node-pty for that session, records `tmuxRuntimeFailure`, and lights the same fallback badge (it is a separate field from `tmuxAvailable`, so the dropdown doesn't call an installed tmux "not installed"). **Use the return value** — `engineType` must record what actually spawned, not what was requested; both WS paths additionally catch so a total failure closes one socket instead of the process.

**The reattach entry is spread from `meta`, not hand-listed.** It is the *third* writer of a shell entry (with the WS restore and spawn paths), and it named its fields by hand — so everything added to `serializeShellEntry` since was dropped on reattach and then wiped from state.json by the next save: `forkParent` (the #497 fork-steal guard), `planMode`, `model`/`effort` (#592), `allowedTools` (#612), `scheduled` (#597). Invisible while almost nobody ran tmux; the default path for everyone now. Pinned by `tmux-durability.test.js`.

**Known gap — #607's *recovery* pass under tmux.** Echo-gated Enter itself works under tmux (`prompt-submit.test.js` asserts it there). What does not is the backstop for a *coalesced* text+Enter when the agent has drawn nothing yet: the daemon reads the pane through an attach PTY, an undrawn window is genuinely unreadable, and `confirmPromptSubmitted` correctly ends `unverified` rather than guessing — `[submit] <id> could not read the composer — not retrying Enter`. That is the designed safe outcome (an indeterminate screen must never trigger a re-send), and submission falls back to the pre-#607 *timed* path, which is what shipped for years. The 607B case is therefore pinned to node-pty. Closing it means making the composer readable through tmux's repaint during an undrawn window.

Tests: `test/unit/engine-default.test.js` (detach contract, offer matrix, ownership rule — **must not import `engines/node-pty`**, see the CI note below), `test/integration-standalone/tmux-durability.test.js` (the acceptance test: SIGKILL *and* SIGTERM the daemon, assert the pane pid is unchanged and the work inside it still running), `test/integration-standalone/engine-migration.test.js`.

**Suites that pin `engine: 'node-pty'` do it deliberately** — via the WS `?engine=` override, or a pre-seeded `settings.json` when it's the whole file. They characterize machinery that only *exists* because a node-pty session dies with the daemon, so under tmux they would wait forever for something that must not happen: `session-restore.test.js` (the whole `--resume` / #542 / bounded-respawn chain — a tmux session is reattached, never respawned), `sleep-reap.test.js` (the detach reaper, which tmux never arms), `window-restore.test.js`'s 30s-grace case (#551's savedState rewrite, which tmux never reaches), and `prompt-submit.test.js`'s 607B + shutdown cases. Each pin says why in place. The tmux side of each is covered by `tmux-durability.test.js`. **Don't add a pin to make a red test green** without checking it's this same "the path is structurally absent under tmux" reason.

**Keep test temp paths SHORT.** `run-standalone.sh` exports a short `TMPDIR` (default `/tmp/ds-test`) because every suite derives its `TMUX_TMPDIR` from `os.tmpdir()`, and macOS's default `/var/folders/<2>/<28>/T/` is 52 characters before the suite's own directory — enough to push the tmux socket to exactly 104 and fail `new-session`. It failed *quietly*: the spawn fallback above keeps the suite green while it tests the wrong engine. `tmux-durability.test.js` asserts `tmuxRuntimeFailure === null` as a tripwire. Running one file by hand skips the runner, so prefix `TMPDIR=/tmp/ds-test` if a suite reports the fallback.

### Session Persistence

Under tmux this is mostly moot — the session never went anywhere; startup reattaches the live pane. What follows is the node-pty path, and the tmux fallback when a pane really did die.

When daemon restarts:
1. SIGTERM triggers `saveState()` → writes shell IDs + cwds + claudeSessionIds to `state.json`
2. `stateFrozen` flag prevents shell `onExit` handlers from overwriting state.json during shutdown
3. On startup, loads `state.json`
4. When client reconnects with saved ID, spawns `claude --resume <claudeSessionId>` in saved cwd
5. If `--resume` fails (exits within 5s), falls back to `claude -c --fork-session --session-id <newUUID>`

**Session records are never hard-deleted by a runtime path (#561).** Every close/kill/wipe — killall, `closeSession()`, `DELETE /api/shells/:id`, natural PTY exit, clear-disconnected — writes a `closed: true` tombstone into state.json (keeping `claudeSessionId`, `cwd`, `worktree`, `name`, `windowId`, plus `closedAt`/`closeReason`), so reconnecting with the shell id can always resurrect the conversation via `--resume`. Never write `delete savedState[id]` in a close path; use `tombstoneSession()` (explicit closes) or `handleShellGone()` (engine `onExit` epilogue — also exposed on the MCP mod context). The only sanctioned purges are an explicit `DELETE /api/shells/:id?forget=1` (what the UI ✕ on an already-closed row sends, and what test cleanup uses) and the retention sweep `pruneClosedSessions()` (`closedSessionRetentionDays` setting, default 30 days; never touches non-closed entries). Every state.json write first rotates the previous file to `state.json.bak`, and the loader falls back to the `.bak` when state.json is missing or corrupt — so a full reset requires deleting both files. **A tombstone resurrects on a plain WS reconnect with its shell id — except when the client sends `noRestore=1`** (#596), which only `app.js`'s server-pushed `open-session` handler does: that connect acts on a session the server said exists, so if it died in the meantime the answer must be `gone`, not a resurrection. Every genuine restore path (restore modal, TabSessions reconnect, orphan claim, recents) omits the flag and is unaffected, and a refused connect leaves the tombstone intact.

**The recover-everything restore surface (#560)** is `GET /api/recoverable-sessions` + `showSessionRestoreModal` (`public/js/session-restore-modal.js`). The endpoint is a superset of `/api/windows` (same `buildWindowsView()` builder — keep them in lockstep): window groups plus the buckets `/api/windows` deliberately omits — `ungrouped` (no windowId, not currently shown in any browser), `closed` (#561 tombstones), and `recents` (ring-buffer lineages absent from state.json, restorable only via the mint-new-id `POST /api/recent-sessions/:key/restore`; everything else restores by plain WS reconnect with the original id, which also consumes the tombstone). Unnamed sessions get a `label` derived from their transcript (`deriveSessionLabel`: the `ai-title` line, else the first user message; first 256KB only, mtime-cached) — derivation lives ONLY in the recoverable endpoint, never in `/api/windows`, which is on every window's startup path. The modal is multi-select (checked-by-default tiers: orphans → closed → recents), dismisses only via its explicit buttons, and is reachable forever from the empty state, the ▾ new-tab menu, and the command palette (`offerSessionRestore()` in app.js); the startup auto-show fires only when orphaned/ungrouped sessions exist, since closed tombstones almost always exist. Cross-window coordination broadcasts `restore-claimed` (claimed ids; other open modals drop those rows) — never a blanket dismiss.

### Security

DeepSteve is **localhost-first with token authentication** (#536). The server binds to `127.0.0.1` by default (overridable with `--bind`). Every surface — the web UI WebSocket, the MCP HTTP endpoint, and all REST/control endpoints — is guarded *before* application code runs by three checks that live in `security.js`:

- **Host allowlist** — rejects any request/WS upgrade whose `Host` hostname isn't `localhost`/`127.0.0.1`/`[::1]`/`deepsteve.localhost` (or a `--allow-host` you add). This is what actually stops DNS rebinding (the rebind domain shows up in `Host`).
- **Origin allowlist** — rejects WS upgrades (and cross-origin cookie-authed HTTP) from any origin but our own (or a `--allow-origin` you add), and rejects a **missing** `Origin` on the WS upgrade. CORS is *not* a substitute — it doesn't protect WebSockets at all.
- **Per-install token** — auto-generated at `~/.deepsteve/auth-token` (mode `0600`). The browser receives it as an HttpOnly, SameSite=Strict cookie set on the page it loads (persistent, 30-day rolling `Max-Age`, re-issued on every page load — #545), so there's no login screen. Non-browser clients (agents, MCP, `restart.sh`) send it as `Authorization: Bearer <token>`; agents read it from `DEEPSTEVE_API_TOKEN`, and the per-session MCP config carries it in a header (written to a `0600` file, never inline in argv). Failed auth attempts are rate-limited; valid credentials never throttle.

**The canonical browser URL is `http://deepsteve.localhost:3000`** (`UI_HOST`/`UI_URL`, #544/#545). Plain `localhost` shares one browser cookie jar with every other local dev app (cookies key on host, not port), and Firefox's per-host cap evicts `ds_auth` when that jar fills — the #544 intermittent-401 bug. `deepsteve.localhost` is still loopback (RFC 6761) but gets its own jar, and makes other localhost apps cross-site so SameSite=Strict excludes them. `canonicalHostRedirect` (`security.js`) 302s browser navigations (`GET` + `Accept: text/html`, no `Authorization` header) on `localhost`/`127.0.0.1`/`::1` to `deepsteve.localhost`, preserving the original port (SSH tunnels) and never touching `--allow-host`/LAN hosts; disable with `--no-canonical-redirect` or `DEEPSTEVE_NO_CANONICAL_REDIRECT=1`. Agent/CLI traffic (`DEEPSTEVE_API_URL`, MCP config, `restart.sh` curls) deliberately stays on plain `localhost` — bearer-authed, no cookies, and must not depend on `*.localhost` resolving for non-browser resolvers. Migrating an existing install moves the UI to a new origin, so open windows lose per-origin localStorage/sessionStorage (window layout, window→session maps) once — server-side sessions are unaffected; recover tabs via recent-sessions restore.

Auth is **always on** with no off switch — the only escape hatches *widen* the allowlists (`--allow-origin`, `--allow-host`, or `DEEPSTEVE_ALLOW_ORIGIN`/`DEEPSTEVE_ALLOW_HOST`). Binding to a non-loopback address (`--bind`) still exposes control to anyone who can reach it: the token is handed to any page the server serves, so it is not a per-user credential across a LAN. **The deploy that first turns auth on must use `./restart.sh --refresh`** so already-open tabs reload and acquire the cookie (a silent WebSocket reconnect has none yet). Tabs running post-#540 frontend also **self-heal**: when a WS upgrade is rejected for auth, the reconnect loops probe `/api/version` (`public/js/auth-heal.js`) and, on a 401/429, force one guarded page reload to re-acquire the cookie — but tabs still running pre-#540 JS can't, so that first deploy still needs `--refresh`.

### Adding a New Setting

Settings are declared once in the `SETTINGS_SCHEMA` array in `server.js`. Defaults, POST `/api/settings` validation, and `broadcastSettings()` all flow from that single entry — you do **not** hand-write a branch in the POST handler or an explicit field in the broadcast payload.

To add a setting, append one entry to `SETTINGS_SCHEMA`:

```js
{ name: 'myNewSetting', type: 'boolean', default: false }
```

Supported `type` values: `string` (opt-in `fallbackOnEmpty` restores the default when an empty string is POSTed), `boolean`, `number` (opt-in `clamp: [lo, hi]`, `round: true`, `fallback` for the NaN/0 case), `enum` (`values: [...]` or `values: () => [...]` for runtime-dependent enums like `engine`), `array` (`itemEnum` filters, `nonEmpty: true` rejects empty writes), and `custom` (provide a `sanitize(raw)` that returns `null` to reject or a cleaned value to accept — for a setting whose shape none of the built-in types cover).

Optional per-entry hooks:
- `broadcast: false` — omit from the WebSocket `settings` message (use for server-internal fields like `wandPlanMode` or binary paths).
- `sideEffect: (val, s) => { ... }` — mutate other settings on accept (e.g. `enabledAgents` re-points `defaultAgent`). Schema declaration order matters: a field later in the array can override a side-effect earlier in the same POST.
- `logValue: v => '...'` — customize the `Settings updated: ...` log line (used by `wandPromptTemplate` and `enabledAgents`).

The client sends fields by name in the POST body and applies them locally on save (`app.js`). Always verify that a second open browser window picks up the change via WebSocket.

**Out-of-schema exceptions:** `activeTheme` and `enabledSkills` intentionally bypass this pipeline — they use dedicated endpoints (`POST /api/themes/active`, `POST /api/skills/{enable,disable}`) and dedicated broadcasts (`broadcastTheme`, `broadcastSkills`) because they ship side payloads (theme CSS) or perform file I/O (copying skill `.md` files). Their defaults live in `NON_SCHEMA_DEFAULTS` next to the schema.

### Command Palette

Cmd+K opens a command palette for keyboard-driven access to tabs, settings, and custom user scripts.

- **Settings**: `commandPaletteEnabled` (default `true`) and `commandPaletteShortcut` (default `Meta+k`) follow the 3-place settings pattern (defaults, POST handler, broadcastSettings).
- **Built-in commands**: Hard-coded in `BUILTIN_COMMANDS` array (new-tab, close-tab, settings, mods, next/prev-tab). Client dispatches these via callbacks.
- **Custom commands**: Executable files in `~/.deepsteve/commands/`. Optional `.json` sidecar for name/description metadata. Executed server-side via `zsh -l -c` (for PATH). Not the same as Skills (which are Claude slash commands in `skills/*.md`).
- **API**: `GET /api/commands` returns built-in + custom commands. `POST /api/commands/execute` runs a custom command by ID.
- **Client**: `command-palette.js` is a self-contained ES module (like `cmd-tab-switch.js`) with `init()`, `setEnabled()`, `setShortcut()` exports.

### Keyboard Shortcuts (`public/js/shortcuts.js`)

**Every global key binding is declared in the `shortcuts.js` registry, and the ⌘? overlay (`shortcuts-help.js`) renders `getAll()`. The list is never hand-maintained** — that's the whole point of #549, and before it there were four independent capture-phase listeners with `parseShortcut`/`matchesShortcut` copy-pasted verbatim into two of them.

The registry is **load-bearing, not documentation**: `register()` returns the matcher the module must use in its `onKeyDown`, so there is no way to change a binding without editing its entry. Call it at **module scope**, not in `init()`, so the entry and the matcher are a single statement that can't be separated.

```js
const matchesShortcut = register({
  id: 'command-palette', group: 'General',
  description: 'Open the command palette',
  getShortcut: () => shortcut,   // live setting value; or `shortcut: 'Meta+f'` if hard-coded
  isEnabled: () => enabled,      // overlay hides the row when this is false
});
```

- **`shortcut` xor `getShortcut`** — either may be a string **or a list of alternates**. Both throw if you pass both or neither.
- **`match: 'key' | 'code'`** (default `'key'`) — `e.key` is the *layout character*, `e.code` the *physical key*. Letters that should survive Dvorak/AZERTY use `'code'` (context-views' ⌘P); punctuation **must** use `'key'` (⌘⇧? is `code:'Slash'` on US but `'Minus'` on German). `match:'code'` throws at import time if paired with `getShortcut` (the settings recorder only emits `e.key` tokens, so it could never fire) or with a key that has no code (`ArrowUp`).
- **Strict modifier equality** is what keeps Ctrl+F reaching the PTY for vim's `<C-f>` while ⌘F opens search. Pinned by a test — don't loosen it.
- **`registerInfo()`** is for bindings the matcher can't express (hold-⌘ tab switching, the ⌘P→A chord, xterm's Shift+Enter). These are *not* enforced, so put them **next to their real handler** and edit them together. `combine: 'then'` renders a sequence, `'or'` (default) renders alternates.
- **`shortcutsHelpShortcut` defaults to a two-item list** (`['Meta+Shift+?', 'Meta+/']`). macOS auto-assigns ⌘⇧/ to the Help menu Search field of any app with a Help menu — Firefox and Chrome both have one — and a menu key equivalent is consumed before the page sees the keydown. ⌘/ is the fallback so the overlay can't ship unreachable. It's a `custom` schema type (not `string`) because the value is a list; `sanitize` also accepts a bare string, which is what the Settings rebind button posts.
- **Tests**: `npm run test:unit`. `test/unit/shortcuts-registry.test.js` asserts the **exact set of registered ids** — if you add or rename a binding, update that list. That is the drift guard.

### Project Mods (#618)

Two kinds of mod, named apart in `docs/mods.md`: **DeepSteve Mods** are what `mods/` has always held — global to the install, every `tools.js` loaded for every session, enable/disable per browser. A **Project Mod** is the opposite: one agent-authored HTML page registered to ONE project (a git repo root), visible only while you're looking at that project, never in a shared store.

- **Naming:** the rail this hangs off is now **Projects**, not Contexts — user-facing strings only (`renderRail`'s header, `+ New project`, the editor, the ⌘? descriptions, the settings section). Every internal identifier is unchanged: `contextViewsEnabled`, `/api/contexts`, `contexts.json`, `{type:'contexts'}`, `.context-*` CSS and `window.deepsteve.onContextsChanged` — so no settings/disk migration and no broken third-party mods. The **Scheduled Tasks panel** had the collision (it called contexts "Groups" and a single repo root "Project"); its vocabulary was fixed *inside the panel* — groups→**Projects**, repo root→**Repo** — with no REST/MCP field renamed. Rail header text is duplicated in `autoSizeRail`'s measurement list (`context-views.js`) — change both or double-click-to-auto-fit sizes against the wrong string.
- **Storage:** registry at `~/.deepsteve/project-mods.json`, one page per mod at `~/.deepsteve/project-mods/<id>.html`. Deliberately **outside the repo**, so "never shared" is a guarantee rather than a gitignore convention — and unlike `display-tabs/` these are **not** stale-swept (durable by definition). Load-on-start / write-through with tmp+rename, the `mods/scheduled-tasks` shape; an orphan sweep at `init()` drops pages with no registry row.
- **Server:** `mods/project-mods/tools.js` — `create/update/edit/list/delete_project_mod` plus `GET /api/project-mods`, `GET /api/project-mods/:id/page`, `PUT`/`DELETE /api/project-mods/:id`. The project is resolved exactly as a scheduled task's is (explicit path → `findGitRoot`, else the caller's `sessionPaths().repoRoot`); unlike a task there is **no homedir fallback** — a project mod with no project is meaningless, so it's an `isError`. `resolveHtml()` (html | file_path | replacements) moved to root `html-source.js` and is shared with display-tab. The `:id` is only ever concatenated into a path *after* matching a registry row, which is what keeps a crafted id inside `PAGES_DIR`.
- **Kill switch:** `projectModsEnabled` (SETTINGS_SCHEMA, default on) is server-authoritative and fail-closed at every **write** — the four mutating tools return `isError`, the REST writes 403 — while `list_project_mods` and both GETs stay open so turning it off can't make existing mods un-inspectable. Same rationale as `scheduledTasksEnabled`: a mod's own enable/disable is per-browser localStorage and never reaches the server.
- **Client (`public/js/project-mods.js`)** owns three surfaces, all of which are host chrome no mod iframe can reach: a **rail** row under the active project (drawn by `context-views.js`'s `renderRail`, which is the one-way import), a **square button** in `#tabs` inserted before `#tabs-list-wrapper` (top of the strip in vertical layout, left of it in horizontal — `.nav-btn.is-glyph` supplies the shape and the collapsed-rail treatment), and a **pinned tab** that auto-opens in the background (#600's no-focus-steal rule) and keeps running while hidden. Scoping is the folder-prefix rule in both directions: with a project selected the mod's repo root must be inside one of its dirs; in **All** the active tab's cwd must be inside the mod's repo root.
- **Two invariants the first build got wrong, both now pinned by tests.** (1) **`render()` must never call back into the rail.** `cb.renderRail()` runs `applyFilter()`, whose `onContextViewApplied` hook calls `render()` — so only `refresh()` may call it, and `render()` additionally carries a re-entrancy guard, because opening a pinned tab runs `notifyTabsChanged()` → `applyFilter()` → `render()`. Without both, the first pinned mod recursed ~1600 deep and no surface finished rendering. `renameProjectModTab` notifies **only when a name actually changed** for the same reason. (2) **The tab id is derived, not minted** — `tabIdFor(modId)` = `pm-<modId>`. A pinned mod is opened from three directions (restore, auto-open, click) and with random ids each was a separate tab that accumulated across reloads; deriving makes a duplicate impossible by construction. `tabNameFor(mod)` prefixes the icon into the **label** because `tabIcon()` reads the chip off the label — otherwise a 📊 mod is a "B" in the vertical rail, where the chip is the whole tab; it is idempotent for the icon-less stub the restore path passes.
- **Trust:** the page is served same-origin and its iframe carries `allow-same-origin` (required to inject `window.deepsteve`), so a project mod has exactly the authority an agent-authored display tab already has. That is a continuation of the existing model — state it in docs rather than pretending the sandbox isolates it.
- Tests: `test/unit/project-mods.test.js` (registry, tools, REST, gate) and `test/unit/project-mods-client.test.js` (scoping, the three surfaces, derived identity, the re-entrancy invariant).

### Skills System

Enabled skills are reusable agent workflows. Their canonical source files live in `skills/*.md`; do not edit installed copies or generated Codex files.

- **Auto-discovery**: The server reads `skills/*.md` and exposes them in `GET /api/mods` with `type: 'skill'`. They appear in the mods UI automatically.
- **Claude install/invocation**: Enable copies the canonical file to `~/.claude/commands/deepsteve/{id}.md`. Claude invokes it as `/deepsteve:{id}` (for example, `/deepsteve:chat #help`). Custom Claude profiles still link their `commands/deepsteve` directory to this shared destination.
- **Codex install/invocation**: Enable generates `~/.deepsteve/codex-skills/deepsteve-{id}/SKILL.md` and links `~/.agents/skills/deepsteve-{id}` to that directory. Codex explicitly invokes it with a skill mention such as `$deepsteve-chat #help`; matching descriptions may also trigger skills implicitly.
- **Codex prompt adaptation**: Codex does not substitute Claude's literal `$ARGUMENTS`. The generated `SKILL.md` changes the frontmatter name to `deepsteve-{id}`, removes Claude-only `argument-hint`, describes arguments as text following the skill mention, and rewrites `/deepsteve:{id}` cross-references to `$deepsteve-{id}`. The source `skills/*.md` remains unchanged.
- **Enable/disable/reconciliation**: Both formats are installed and removed together. Startup reconciliation restores enabled artifacts and removes disabled known artifacts. Correct links/files are left unchanged, stale managed Codex links are repaired, and a non-symlink path at `~/.agents/skills/deepsteve-{id}` is logged and never overwritten.
- **Frontmatter**: Each source file has YAML frontmatter with `name`, `description`, and optional `argument-hint`.
- **Focused test**: `node --test --test-timeout=180000 test/integration-standalone/codex-skills.test.js`.

### Scheduled Tasks (locally-queued cron)

The `scheduled-tasks` mod (`mods/scheduled-tasks/`) runs recurring agent tasks **on this machine** on a cron schedule. Unlike Claude Code's cloud `/schedule` (egress-restricted), a scheduled run is just a normal local Claude session, so it gets the project's MCP servers for free — the intended use is recurring MCP-dependent work (e.g. a weekly analytics report). Issue #521.

- **Self-contained tasks**: each task stores its own `prompt` + canonical `project` (git repo root) + 5-field `cron`. Persisted to `~/.deepsteve/scheduled-tasks.json`; project groups (named sets of repo roots) live in `~/.deepsteve/project-groups.json`. Both use the load-on-start / write-through pattern (like `mods/tasks/`).
- **Scheduler lives in the mod**: `init(context)` (called by `initMCP`) starts a `setInterval` tick (~30s) using the spawn helpers on the shared `context` object; the run recipe mirrors `/api/start-automation` (`spawnSession` → `shells.set` → `wireShellOutput` → `emitSessionOpen` → `deliverPromptWhenReady` → `deliverToWindow`). No windowId / no forced browser — unattended runs queue their tab via `pendingOpens` and surface when a browser next connects, **if the run is still alive by then** (#596, see below). `server.js`'s only contribution is the `scheduledTasksEnabled` kill-switch setting.
- **Cron is local time**, 5 fields (`min hour dom mon dow`), parsed/matched by `mods/scheduled-tasks/cron.js` (dependency-free; supports `*`, `n`, `a,b`, `a-b`, `*/n`; classic dom/dow OR rule). The UI offers preset builders (hourly/daily/weekly/monthly) plus a raw field.
- **Catch-up once**: on startup (after a ~10s settle), any enabled task whose `nextRun` is in the past runs **once**, then resumes — one catch-up per task regardless of how many occurrences were missed. An **overlap guard** skips firing if the task's previous run's session is still alive **and hasn't self-reported terminal** (`ACTIVE_STATUSES`), so a finished-but-idle tab no longer blocks the next fire.
- **Agent self-reports completion (#525)**: an interactive Claude REPL doesn't exit when it finishes, so completion can't be inferred from the PTY. Instead the scheduled-run prompt is wrapped (only when MCP is wired for the agent — `mcpConfigArgs(...).length > 0`, i.e. claude) with a contract telling the agent it's a scheduled run and to call `scheduled_task_started` when it begins and `scheduled_task_finished` (with `success` + a one-line `summary`) when done. Run status lifecycle: `queued` → `running` → `succeeded`/`failed`, with `ended` as an onExit fallback for a session closed with no self-report. The onExit fallback is **skipped during shutdown** (the session persists + resumes with the same shellId, so it can still self-report after restart). Each run stores `{ startedAt, sessionId, status, endedAt, agentStartedAt, success, summary }`; the tool identifies the caller's run via the `?shellId=` in its MCP URL (`findRunByShell`). Legacy `started`/`completed` rows still render in the panel badge.
- **The fire pre-permits its own contract tools (#612)**: deepsteve imposes the self-report contract, so deepsteve makes it callable — `runTask` spawns with `--allowedTools mcp__deepsteve__scheduled_task_started,mcp__deepsteve__scheduled_task_finished`. Before this, whether an unattended run could honor the contract depended on whatever `settings.json` allowlist happened to exist in the target project, and the default path was the worst case: per-run worktree isolation (#565) puts the run in a fresh claude-native worktree with no inherited permissions (`symlinkWorktreeSettings` only covers the *manual* `ensureWorktree` path). A run that blocked on `Do you want to proceed?` never self-reported, so its status stayed `running` forever, the overlap guard skipped **every subsequent fire** of that task, and only `maxRuntimeMinutes` unwedged it an hour later as `timed-out`. Plumbing mirrors #592's model/effort exactly: `allowedToolsFlag` in `AGENT_CONFIGS.claude` → `allowedToolsArgs()` → **both** `getSpawnArgs` and `getResumeArgs` (Claude's `--resume` carries no session flags), with `allowedTools` in `serializeShellEntry` so a restart-resumed run keeps the grant. Names are re-validated at the argv boundary by `validateToolName` (capped at `MAX_ALLOWED_TOOLS`, and the `Bash(git *)` specifier form is deliberately rejected), so a hand-edited `state.json` can't inject arguments. The array is generic and mod-supplied — `CONTRACT_TOOLS` lives in the scheduled-tasks mod, gated on the same `mcpWired` probe that decides whether to inject the contract at all, so core stays agnostic. **Deliberately narrow**: only the two self-report tools. A run can still wedge on a Bash/Edit prompt mid-task and never reach `scheduled_task_finished` — `maxRuntimeMinutes` remains the only backstop for that.
- **Auto-close (per-task, default on)**: `scheduled_task_finished` auto-closes the (unattended) tab unless the task's `keepOpen` (never close) or `keepOpenOnFailure` (keep a failed run open) flags are set — both default `false` and are set at creation via the form checkboxes or the `keep_open`/`keep_open_on_failure` MCP/REST fields. Closing goes through `ctx.closeSession` (acks the tool response before teardown; the now-terminal run status means the onExit fallback won't overwrite it).
- **Background open (#600, `scheduledTasksOpenInBackground`, default on)**: a scheduled fire is unattended, so its `open-session` message carries `background: true` and the tab lands **inactive** — no focus steal, and no `revealTabContext()` yanking the context rail. `runTask(task, reason, { foreground })` computes the flag live off `ctx.settings` (no restart to toggle). Background is the default for schedule fires, catch-up fires and the agent-facing `run_scheduled_task_now` MCP tool; only the panel's own Run-now button (`POST /api/scheduled-tasks/:id/run`) passes `foreground: true`, since the user just asked to see that run. Client side (`initTerminal`, app.js): `if (!restoreActive && (!background || !activeId)) focusTab(id)` — it *does* focus when nothing is active yet, or a lone inactive tab would leave a blank pane behind a hidden empty state; otherwise it gets the unseen-activity badge so it's discoverable. Background opens also skip `progressStart` (the top-of-page progress bar is ambient interruption for work the user didn't start), which is why `progress-bar.js`'s `done()` now early-returns for an id that never called `start()`.
- **Unattended runs must survive having no browser at all (#596)**. Three things used to break in exactly that case, all fixed:
  - **The queued tab outlived the run.** `pendingOpens` is now the self-cleaning queue in `pending-opens.js` (TTL 24h, cap 100, injectable clock — unit-tested standalone). Entries are dropped the moment their target closes (`tombstoneSession()` / `deleteDisplayTab()`, the universal funnels) and re-checked for liveness at flush via `isPendingOpenLive()`. Before this, a run that fired, finished and auto-closed with nobody watching still handed its tombstoned id to the next window, which reconnected with it and got a zombie `claude --resume` tab pointing at a worktree `cleanupWorktree` had already deleted — one per unattended fire. Unknown (mod-defined) message types are never dropped for liveness, only by TTL/cap.
  - **The auto-updater restarted through live work.** `POST /api/request-restart` auto-confirms when zero browsers are connected — which is the unattended case by definition — so the 6-hourly update check killed runs mid-work, leaving `status: 'running'` forever (shutdown skips the run's `onExit`) and leaking the worktree (`sweepLeakedWorktrees` skips ACTIVE runs). `scheduleAutoApply()` now consults `restartBlockers` (registered via the `registerRestartBlocker` ctx hook) and defers in 10-minute steps, up to 6 times, then applies anyway so a wedged run can't starve updates. The mod blocks only for a run that is ACTIVE, has a live shell, and has **no** attached client — a tab someone is watching belongs to them. Deliberately unchanged: an explicit `./restart.sh` is a direct user instruction and still restarts immediately.
  - **A stuck run wedged its task forever.** Nothing reaps an unattended session (`armDetachReap` only arms from a WS `close`, and there was never a socket), so a run parked on a permission prompt kept the overlap guard skipping every future fire. Each task now has `maxRuntimeMinutes` (default 60, `0` = unlimited; settable via the panel, `max_runtime_minutes` on `schedule_task`/`update_scheduled_task`, or the REST body). `enforceRunTimeouts(now)` runs at the head of each tick and closes an over-limit clientless run with status `timed-out` — deliberately **not** an ACTIVE status, so the `onExit` fallback leaves it alone, the worktree sweep reclaims it, and the next fire is unblocked.
  - Related: `browser_eval` / `browser_console` / `screenshot_capture` now return an immediate `isError` when no browser window is connected, instead of broadcasting into the void and timing out after 10s/30s with a misleading "enable the mod" message.
- **Per-run worktree isolation (#565, per-task `isolateWorktree`, default on)**: each fire of a claude task on a git-repo project runs in its own disposable Claude Code worktree `scheduled-<shellId>` (branch `worktree-scheduled-<shellId>`, created by claude's native `--worktree`), so scheduled runs never clobber the main checkout. The prompt contract adds a merge-back clause: commit + merge/push anything worth keeping BEFORE `scheduled_task_finished`. Cleanup runs from the run's `onExit` (after auto-close, manual close of a kept-open tab, or a crash-'ended' run — never during shutdown, so a restart resumes the same worktree via the persisted `entry.worktree`): `cleanupWorktree()` uses `git worktree remove` **without** `--force` (dirty worktree → kept, with its branch) then `git branch -d` (unmerged → branch kept). A daemon restart replaces the mod's onExit with the core restore handler, so `sweepLeakedWorktrees()` (startup + each tick, one attempt per run per process) reclaims terminal-status runs whose tab is gone and whose state.json record is `closed` — checked via `ctx.getSavedSession`, the one initMCP addition. Non-claude agents, non-repo projects, and the homedir fallback all skip isolation and run exactly as before. Run rows record `worktree`/`worktreeRemoved`; the panel shows "(kept)" for preserved worktrees.
- **Per-task model / effort / config profile (#592)**: `model` (alias like `opus`/`haiku`, or a full id like `claude-fable-5`), `effort` (`low|medium|high|xhigh|max`), and `configProfile` (a #537 custom-config-profile **id**) are per-task fields, settable from the panel form and from `schedule_task`/`update_scheduled_task` (`model`, `effort`, `config_profile`) and REST. All three are **claude-only** and default to `null` = inherit Claude Code's own default — which is what every pre-#592 run did, including the silent fallbacks off Opus on usage limits that the issue's 54-run audit surfaced. Plumbing: `AGENT_CONFIGS.claude.modelFlag/effortFlag` → `modelArgs()` → **both** `getSpawnArgs` and `getResumeArgs` (Claude's `--resume` doesn't persist session flags, same reason `--permission-mode` is re-applied), with `model`/`effort` in `serializeShellEntry` so a restart-resumed run keeps them. Values are re-sanitized at the argv boundary by `validateModel`/`validateEffort` (exposed on the mod ctx alongside `resolveConfigDir`), so a hand-edited `scheduled-tasks.json` can't inject arguments. The profile is stored as the **id**, not the resolved dir (a task is a template — editing the profile's directory in Settings should move future runs with it) and resolved per fire via `ctx.resolveConfigDir`; `runTask` was previously the only spawn path in the codebase that never passed `configDir`. Each run row records the **effective** `model`/`effort`/`configDir` (the panel shows them as a `haiku · low` chip in History) — nothing else stores them, and effort appears in no transcript at all. The panel's agent dropdown now comes from `GET /api/agents` instead of a hardcoded list, so profiles appear as a `config:<profileId>` optgroup (the same encoding the main new-tab menu uses; `splitAgentSelection` accepts it on every write path) and `codex` is no longer silently missing.
- **System-level default model / effort (#604)**: `scheduledDefaultModel` (string, default `''`) and `scheduledDefaultEffort` (enum `'' | low…max`, default `''`) are the fallback for any task that pins neither — so a policy like "every automation runs Sonnet + medium" is set once in Settings → Scheduled Tasks instead of per task, and a task an agent creates later via `schedule_task` without `model`/`effort` can't escape it. Resolution per fire in `runTask()`: `cleanModel(task.model) || defaultModel()` (ditto effort), where `defaultModel`/`defaultEffort` read **live** off `ctx.settings` — same as the `scheduledTasksEnabled` gate — so a Settings change applies to already-created tasks on their next fire with no restart. `''` = inherit Claude Code's own default, i.e. pre-#604 behavior. The setting is sanitized twice: `validateModel`/`validateEffort` in the schema entry (so a bad value is *rejected at POST time* with a `warnings` entry rather than silently no-op'ing at fire time) and again via `cleanModel`/`cleanEffort` at the argv boundary — a settings value is no more trusted than a task value. Nothing downstream changes: the run row still records the **effective** values, so history shows the resolved default. `GET /api/scheduled-tasks` also returns `defaults: {model, effort}` so the panel form's "Default" options read `Default (system: sonnet)` instead of a vague "inherit"; both schema entries carry a `sideEffect` that re-broadcasts `scheduled-tasks` so an open panel relabels immediately. Tests: `test/unit/scheduled-default-model-effort.test.js`.
- **A task is never hard-deleted while one of its runs is in flight (#614)**: `task.runs` is the *only* record of the run↔session link (`findRunByShell` matches `run.sessionId` against the caller's `?shellId=`), so splicing a task out mid-run orphaned the live agent it had spawned — `scheduled_task_started`/`scheduled_task_finished` answered "this session is not a scheduled task run", the run was never recorded, the unattended tab never auto-closed (auto-close lives *inside* `scheduled_task_finished`), and `enforceRunTimeouts` + `sweepLeakedWorktrees` lost it too. `deleteTask()` now always unschedules immediately but, when `activeRunOf(task)` is set, keeps the row as a **tombstone** (`deleted: true` + `deletedAt`, `enabled: false`, `nextRun: null`) instead of splicing — the same rule as the #561 session tombstones: a delete may not destroy a record something live still depends on. The split is one accessor: **`liveTasks()`/`findLiveTask()`** for everything that schedules, lists or mutates a schedule (`tick`, `runCatchUp`, `list_scheduled_tasks`, `updateTask`, `run_scheduled_task_now`, `GET /api/scheduled-tasks`, `POST /:id/run`, `knownProjects`), and the **full `tasks`** for everything that reasons about a *run* (`findRunByShell`, `enforceRunTimeouts`, `sweepLeakedWorktrees`, `unattendedRunInFlight`, the run's `onExit` epilogue). A tombstone is invisible everywhere — panel and every `list_scheduled_tasks` scope — and `purgeTombstonedTasks(now)` (in `tick()`, right after `enforceRunTimeouts` so a reaped run releases its row the same pass; saves itself like its sibling, and deliberately **not** called from `runCatchUp` since a restart-resumed run is still ACTIVE) drops it once nothing needs it. Two things pin a tombstone: an ACTIVE run, and **a run holding an unreclaimed worktree** (`run.worktree && !run.worktreeRemoved`) — the tick purges *before* `sweepLeakedWorktrees()` runs in the same interval callback, and after a restart the sweep is the only thing that reclaims a worktree, so purging first would leak the directory permanently. A 7-day `TOMBSTONE_TTL_MS` is the backstop for both (a shell that died so hard nothing moved its status off ACTIVE; a worktree git refuses to remove). The same defect had a second route: `MAX_RUNS` truncation, now `trimRuns()`, which never evicts a row whose `sessionId` is still in `ctx.shells` (a `keepOpen` tab can outlive 20 later fires). `DELETE /api/scheduled-tasks/:id` returns `{deleted, tombstoned, activeSession}` and the panel's delete confirm warns when the newest run is still active. Tests: `test/unit/scheduled-task-tombstone.test.js`.
- **The self-report tools tell the truth about a missing record (#614)**: `noRunResult()` replaced the bare "This session is not a scheduled task run — nothing to mark", which was unfalsifiable — now that a delete keeps the record, reaching it really does mean there is no run, so it names the causes (usually a **resumed or forked conversation replaying the original run's ⏰ header under a new shellId**), says the work itself is unaffected, and hands back `list_scheduled_tasks scope:"all"` + `unschedule_task`. It is *not* `isError` (a no-op notice, not a failure). A run whose schedule was tombstoned still reports normally, with `deletedScheduleNote()` appended. `unschedule_task` returns three distinguishable answers — unscheduled / already unscheduled / no such id — instead of one ambiguous `not found`, so an agent winding its own recurring task down can always get a definitive result using the id from its ⏰ header, whether or not the task appears in a listing. `createTask`/`deleteTask` also log now; before, a deletion left no trace at all and had to be inferred from a *missing* "skipped — previous run still active" line.
- **Panel: inline edit + active-first ordering (#613)**: `Edit` swaps `TaskForm` into the task's **own row slot**, in place of its card — it no longer renders as a sibling above every section, which used to insert ~500px at the top of the panel and throw the row you clicked off-screen. Each row is a keyed `<div data-task-id>` holding either the card or the editor, and that key is load-bearing twice over: it forces a fresh `TaskForm` mount when you go straight from editing one task to another (the old top-level form had no `key`, so it kept the first task's field values while saving to the second's **id**), and `data-task-id` survives the card↔editor swap so the `useLayoutEffect` scroll pin can restore the row's top edge by id after commit. Only `+ New` still renders at the top (`editing` is `{mode:'new'}|{mode:'edit',id}`; it pins `toTop`). `editing` holds an **id, never the task object** — every `scheduled-tasks` broadcast, including a plain scheduler tick, replaces the whole `data.tasks` array, so a held object goes stale; the live task is re-resolved from `sections` each render. Two guards close a dangling editor: the edited task disappearing (deleted here, in another window, or via `unschedule_task`) and any `filter` change. Ordering: the `sections` memo puts **active tasks first** (`isActive` = enabled and not a fired one-shot), as a *partition* so each tier keeps its existing creation order, and sinks whole project sections that have nothing active below the ones that do — otherwise one live task among a hundred paused ones sits at the bottom of the panel. Consequence by design: pausing a task moves its row down on the next broadcast. Client-render only — no REST/MCP/persistence surface changed, and no sort control was added.
- **Scoping**: `list_scheduled_tasks` defaults to the caller's own project (`sessionPaths(entry).repoRoot`); `scope:'group'` adds sibling repos sharing a project group; `scope:'all'` lists everything. MCP tools: `schedule_task`, `list_scheduled_tasks`, `update_scheduled_task`, `unschedule_task`, `run_scheduled_task_now`, `scheduled_task_started`, `scheduled_task_finished`. The panel (right side) groups tasks by project, with a scope filter, run history (with per-run summary), and group management.
- **`scheduledTasksEnabled` setting** (default on) is the master switch and the server-authoritative on/off — the correct gate because a mod's UI enable/disable is client-side only (per-browser localStorage; never reaches the server). The tick reads it live (settings object is mutated in place), so toggling it in Settings stops/starts the scheduler with no restart. The **same gate is fail-closed at every write/action surface**: the MCP tools `schedule_task`/`update_scheduled_task`/`run_scheduled_task_now` return a clear `isError` "feature turned off" result (`featureOffResult`, `FEATURE_OFF_MSG`) and the matching REST writes (POST create, PUT update, POST `/:id/run`) 403 with the same message — so an agent scheduling into a disabled feature learns why instead of getting a cheerful ack for a task that will never fire. Deliberately **not** gated: `list_scheduled_tasks` (read), `unschedule_task` (cleanup should always work), and `scheduled_task_started`/`scheduled_task_finished` (a run already in flight when the switch flips off must still self-report + clean up). The scheduler timers are `.unref()`'d so `init()` is unit-testable (`test/unit/scheduled-feature-gate.test.js`).

### Sleep Resilience (#563)

macOS sleep freezes the daemon and suspends browser pages at *different* times (DarkWake runs the daemon ~45s while pages stay frozen), which used to reap live sessions ("disconnected") and stall reconnects after every wake. Four cooperating pieces:

- **`sleep-watch.js`** — dependency-free 5s tick; a >20s wall-clock gap between ticks means the daemon was frozen → records `lastWakeAt`. Consumers call `holdoffRemaining(ms)` before treating client silence as absence.
- **Sleep-aware detach reaper** — `armDetachReap()` (server.js) wraps both 30s detach grace timers (terminal + tmux-attach). Note that since #620 a **tmux-backed session never arms it at all**: it stays live with no client, so the sleep problem below simply doesn't arise for the default engine — this matters mainly for node-pty installs and `tmux-attach` tabs now. At fire time it re-arms instead of reaping if the daemon woke within `DETACH_HOLDOFF_MS` (120s) **or** the timer itself fired >10s late — the late check matters because overdue timers run in due-time order after a freeze, so the reaper can otherwise beat sleep-watch's own overdue tick. Net: a session is only reaped after 120 *contiguous daemon-awake* seconds with no client, so a post-wake reconnect always wins. Test overrides: `DEEPSTEVE_DETACH_GRACE_MS` / `DEEPSTEVE_DETACH_HOLDOFF_MS`. The reload-channel heartbeat similarly re-pings instead of terminating on the first missed pong after a wake.
- **`power-assertion.js`** — while any session is open (and `preventSleepWhileActive` is on, the default), the daemon holds `caffeinate -i -w <pid>` so the Mac doesn't idle-sleep out from under live sessions (availability must not depend on a user-managed caffeinate tab). Reconciled by a 5s `sync()` tick rather than hooks at the six `shells.set` sites; `-i` deliberately does **not** block clamshell sleep; macOS only.
- **Client wake watch + liveness probe** — `public/js/wake-watch.js` detects wake (`visibilitychange`, `online`, timer-gap) and `ws-client.js` reacts: sockets mid-reconnect retry immediately, and OPEN sockets (which may be dead without an `onclose` after sleep) are probed with `{type:'ping'}` → force-close + reconnect if no traffic arrives in 5s (wall-clock-checked, because throttled background tabs batch timers). **Probes are capability-gated on `pingPong: true` in the server's `session` message** — unknown control messages fall through to the PTY write, so an old server would type the probe JSON into the terminal. A brand-new session attempted while the server is unreachable shows a shared "Server unreachable…" banner with Cancel (`trackPendingCreate`, app.js) — the WS retry loop already queues the create; the banner just makes it visible.

Simulating sleep in tests: `SIGSTOP`/`SIGCONT` the daemon (see `test/integration-standalone/sleep-reap.test.js`).

### Gotchas and Non-Obvious Behavior

- **tmux's default socket is per-UID, NOT per-HOME**: `engines/tmux.js` uses the default socket (`$TMUX_TMPDIR`-or-`/tmp`/`tmux-<uid>/`), so a second daemon started with a scratch `HOME` still sees the real daemon's `ds-*` tmux sessions. Any isolated/test daemon MUST still point `TMUX_TMPDIR` at a scratch dir (`test/run-integration.sh` does) — it keeps the suites from tripping over each other's sessions. **And it must `mkdir` that dir, not just set the variable:** tmux falls back to `/tmp` when it can't use the directory, silently putting the test daemon's sessions on the real per-UID socket — precisely the failure the variable exists to prevent. `meta-consent-rc-inherit.test.js` set it without creating it and leaked a `ds-*` session onto the developer's own socket on every run once #620 made tmux the default (before that it spawned node-pty and created no tmux session at all, so the bug was invisible). What it is no longer the *only* thing standing between you and data loss: startup used to **destroy any `ds-*` session missing from its (scratch) state.json as an orphan**, so one forgetful test daemon wiped every live agent on the box. Since #620 the rule is **destroy only what this daemon can positively identify as its own and finished**: a session absent from our state.json is logged and left strictly alone, and only a session whose own state.json record is a `closed` tombstone (the kill didn't take) gets reclaimed. Consequence by design: a genuinely orphaned `ds-*` session is never garbage-collected, so `tmux kill-session` is the manual out.
- **tmux is invoked directly, never through a shell (#619)**: every tmux call is `execFileSync(<resolved absolute path>, argv)` — `engines/tmux.js`'s `_exec()`, plus `hasSession()`/`listAllSessions()`, which exist so `GET /api/tmux-sessions` and the WS `tmux-attach` path stop running tmux themselves. It used to be `zsh -l -c 'tmux …'` everywhere, which quietly made the whole engine conditional on **zsh** being installed: on a Linux box with tmux and no zsh the probe threw, `available` was false, `settings.engine` was rewritten back to `node-pty` at startup and the option vanished from Settings — reported as the useless "tmux not available". Resolution now lives in **`tmux-path.js`** (root-level so `restart.sh`'s `cp *.js` and `release.sh`'s `for rootjs in *.js` ship it automatically; `engines/`'s embed list is hand-maintained): a pure-`fs` scan of `$PATH` and then `FALLBACK_DIRS`. **`/opt/homebrew/bin` is in that list because the LaunchAgent plist PATH omits it** (`release.sh`) — that omission is the entire reason a login shell was there, so don't "simplify" the fallback list away. `tmuxBinary` (setting, default `tmux`) is the escape hatch for a nix/asdf/custom-prefix tmux; it applies on restart, since the engine probes once at construction. The unavailable path now names the binary and every dir searched. Two things that are *not* changing: `shellQuote()` stays (it quotes the shell-command string **tmux itself** runs via `$SHELL`, which is a different layer), and `#{session_width}`/`#{session_height}` come back empty on modern tmux (3.6) and parse to NaN — pre-existing, same format string as before, and unobserved since the submenu renders only name + attached. Tests: `test/unit/tmux-path.test.js`, which is the coverage the issue says nothing had — the CI unit job runs bare on ubuntu-latest with **no zsh** and `--ignore-scripts`, making a fake tmux on disk there literally "tmux present, zsh absent". **`--ignore-scripts` means node-pty's native binding is never built, so nothing under `test/unit/` may import `engines/node-pty`** (requiring it throws). `engines/tmux.js` *is* importable there as of #620, which made its node-pty require lazy — it is only needed at attach time, and callers that inject `spawnPty` never load it. That is what let the detach/exit contract get unit coverage at all.
- **Prompt readiness is LEVEL-triggered, not edge-triggered (#607)**: `deliverPromptWhenReady` used to park a queue head on a one-shot `e.onIdleOnce` that `setWaiting` fired only on the `false→true` transition. When the screen classified `'unknown'` at drain time while `e.waitingForInput` was **already true**, that edge had already passed — `reclassifyWaiting` no-ops on `'unknown'` and `setWaiting` early-returns on a no-change — so the callback could never fire and **the prompt was never even typed**. Reachable for the 2nd queued prompt (an inherited `/rc` followed by the issue prompt) and for the async `fetchIssueFromGitHub` path, which arms delivery seconds after the tab has already gone idle; worse, a later `'working'→'waiting'` pass would inject the stale prompt as a surprise. It is now `e.pendingDelivery`, served by `servePendingDelivery()` from inside `reclassifyWaiting` — which already runs on **both** the PTY data path and the 1s waiting sweep, so no new timer is involved. A `PROMPT_READY_DEADLINE_MS` (30s) submits anyway if the screen never becomes decisive, counting **ambiguous time only** (a `'working'` screen pushes the deadline out, so a long turn never gets a prompt shoved into it). `onIdleOnce` is gone; `onCodexReadyOnce` is unaffected because its arm site already checks the level.
- **Ink input parsing / confirmed submission (#607)**: `shell.write("text\r")` doesn't work for submitting to Claude — Ink only recognizes Enter when `\r` arrives as its **own stdin read**, so `submitToShell()` writes the text and the `\r` separately. The fixed 1s gap that used to separate them was only ever a *proxy* for "Ink consumed the text": under load (many tabs, a cold start, a busy machine) the child can go longer than that without servicing stdin, both writes sit in the tty buffer, one `read()` returns them together, and the prompt ends up **staged in the composer and never sent**. Three things now make submission confirmed rather than assumed:
  - **Echo-gated Enter.** `submitWithConfirmedEnter` writes the text, then waits for `entry.outputSeq` to move (a monotonic PTY-chunk counter — output after our write proves the child read it) *and* for `readComposerDraft()` to see a non-empty composer, before sending `\r`. Capped (`echoMaxWaitMs`), with a `PROMPT_ECHO_MIN_GAP_MS` floor so a false-positive confirm can never make the gap *shorter* than the old 1s.
  - **Verify and retry.** `confirmPromptSubmitted` polls afterwards and re-sends **`\r` only, never the text** (re-typing would duplicate the prompt if the first Enter merely landed late) when the agent is idle *and* `isPromptStaged()` says our prompt is still in the composer. It bails on a running turn, on any non-ours write to the PTY, and on a screen it can't read — an indeterminate window ends in `unverified`, not a retry. Silence extends the window rather than burning it: a frozen child's last frame predates our typing, so reading it as "not staged" is the exact #607 misread.
  - **`composer-state.js`** is where "is it still staged" lives, and it must consult **only the composer box** — after a successful submit the prompt text is still on screen as a transcript line, so a whole-screen substring test reports "staged" every time and double-submits every prompt. (`isPromptOnScreen()` is the opposite, deliberately naive, whole-screen check, used only as positive evidence that the agent *received* the prompt.) `❯` is also the selection cursor of permission dialogs and AskUserQuestion menus, and an empty composer still carries a placeholder hint — both are fixtured in `test/unit/fixtures/composer-screens.js`.
  - Gated by the `promptSubmitVerify` setting (default on, read live) and scoped to screen-classified agents (claude). `killShell`'s `/exit` deliberately stays on the timed path — it disposes `entry.terminalScreen` and drops the data handler *before* submitting, so echo could never confirm and every shutdown would burn the cap. Hence `confirmEcho` is **opt-in per call**, set only by `drainPromptQueue`.
  - Timings are env-overridable (`DEEPSTEVE_SUBMIT_ECHO_*`, `DEEPSTEVE_SUBMIT_VERIFY_*`, `DEEPSTEVE_PROMPT_READY_DEADLINE_MS`) and budgeted **together** to stay under the 60s `inputBlockTimer` / client banner: 30s readiness + 5s echo + 16s verify = 51s. Raising one means re-checking the others (a unit test asserts it).
  - Tests: `test/unit/{composer-state,prompt-submit,prompt-delivery}.test.js` and `test/integration-standalone/prompt-submit.test.js`. **The bash stubs every other standalone suite uses cannot see this bug** — bash `read` is line-oriented and the pane is in canonical mode, so text+`\r` always arrives as one line whether or not the daemon split the writes. The repro needs `test/helpers/stubs/fake-claude-tui.js`, a raw-mode node TUI that models Ink's own-read rule and whose `readAfterMs` policy withholds stdin service so coalescing happens **at the file descriptor**, by construction. `DS_KEEP_TMP=1` preserves its stdin/event logs.
- **BEL detection / waiting classifier**: Claude emits `\x07` (BEL) when it reaches its input prompt — its "I need attention" signal. The server tracks `lastBelTime` (and `lastInputTime`, set whenever input is written to the PTY). `waitingForInput` flips true only after ~2s of PTY silence **and** a BEL has fired since the user last submitted (`lastBelTime >= lastInputTime`) — so a long, quiet tool call (bash, slow network) is no longer mis-classified as "waiting" (#500). Sessions that have never emitted a BEL (terminal bell disabled) fall back to the legacy silence-only heuristic. This `waitingForInput` state drives browser notifications, the hash-commands overlay, the overview waiting dot, the Action Required auto-cycle mod, and auto-submission of `initialPrompt`.
- **Graceful shutdown**: The shutdown sequence tries `/exit` first (with Ctrl+C interrupt if Claude is busy), waits 8s, then SIGTERM, then 2s more, then SIGKILL. Process group kills (`-pid`) are attempted first for child process cleanup.
- **Two-tier session storage on client**: `TabSessions` (sessionStorage) is the authoritative per-tab source that survives page refresh. `SessionStore` (localStorage) is for cross-tab/window coordination (orphan detection, restore modal). **Every mutation of both goes through the single write facade `public/js/session-stores.js` (#385) — `SessionStores.add/remove/rename/reorder` write both stores in one call, so they can't drift; app.js never mutates either store's session list by hand.** `TabSessions` now lives inside that module (unexported), so it can only be written via the facade; reads use `getTabSessions()` / `SessionStore.getWindowSessions()`. The facade owns *dual* writes and *all* `TabSessions` writes (incl. the TabSessions-only `updateId`/`setClaudeSessionId`/`clearTabSessions`/`addTabOnly`); `SessionStore`'s standalone window/pref writes (`addRecentDir`, `touchWindow`, `claimSessions`, dir-picker prefs) have no `TabSessions` twin and stay direct.
- **Orphan detection**: Uses BroadcastChannel for cross-tab heartbeats. When a new tab opens and finds localStorage windows with no heartbeat response within 1.5s, those sessions are offered for restore.
- **Scrollback buffer**: Each shell keeps a ~100KB circular buffer. On reconnect/restore, the full buffer is replayed to the terminal before any new output, so you see history.
- **`restart.sh` runs in background**: It re-execs itself with `nohup` so the terminal returns immediately. Use `--refresh` flag to force browser page reload (vs silent WebSocket reconnect).
- **Terminal tab persistence on restart** (the **node-pty** story — under tmux, since #620, the process itself survives and startup reattaches the same live pane): Plain terminal tabs (`agentType: 'terminal'`, spawned via `open_terminal` or the `deepsteve:terminal` skill) are persisted in `state.json` the same way Claude sessions are, and are restored on reconnect by re-spawning `zsh -l` in the saved `cwd`. What survives: the tab, its name, and its `cwd`. What does NOT survive: running processes (SIGTERM/SIGKILL during shutdown), the scrollback buffer (in-memory only), and any env set during the session. `--refresh` does not change what's persisted — it only controls whether the browser force-reloads vs. silently reconnects its WebSocket; the server-side restore path is identical.
- **`open_terminal` opens a PLAIN TERMINAL by default — pass `agent_type` for a Claude session:** The `open_terminal` MCP tool (`mods/deepsteve-core/tools.js`) defaults to a plain `zsh` terminal, **not** a Claude/agent session, and it does **not** auto-inherit the caller's agent type — the resolution is `effectiveAgentType = agent_type || (fork ? caller.agentType : null)`, so with neither `agent_type` nor `fork` you get a plain shell. To open a Claude Code session (one that runs slash commands like `/rc` and actually receives `prompt`) you **must** pass `agent_type: "claude"` (or `fork: true` to inherit the caller's agent). Without `agent_type`/`fork`, `prompt` is silently **ignored** and only `command` runs. Symptom of getting this wrong: the new tab comes up as `agentType: "terminal"` in `GET /api/shells`. (The tool's own MCP `description` was previously misleading on this — it claimed to "inherit agent type from the caller"; fixed to state the plain-terminal default explicitly.)
- **`release.sh` generates `install.sh`**: The installer is a single self-contained bash script with all source files embedded as heredocs (text) or base64 (images). Binary images are base64-encoded. `install.sh` is NOT checked into the repo — it is generated on demand and attached to GitHub releases.
- **node-pty**: Uses `.removeListener()` not `.off()`. Must `delete env.CLAUDECODE` when spawning nested Claude instances.
- **LaunchAgent PATH**: `execSync` uses `/bin/sh` without Homebrew paths. Commands like `gh` and `git` must be wrapped in `zsh -l -c '...'` to get the user's full PATH.
- **Worktrees**: Sessions can be created with a `--worktree <name>` flag that's passed through to Claude Code. The worktree name is persisted in state.json for restore. `./restart.sh` deploys from wherever it lives (`dirname $0`), so the worktree's own `./restart.sh` *does* copy that worktree's contents to `~/.deepsteve/` — useful for testing in-worktree changes without merging. Caveat: it stamps the worktree path into `.install-source.json` (which the in-app auto-update's `git pull` runs against), so for a durable install prefer running `./restart.sh` from the main checkout after merging.
- **Claude Code 2.1.222 isolates worktree sessions, which broke `/deepsteve:merge` (#617)**: 2.1.222 turns on a guard that statically parses every Bash command in a worktree-isolated session and refuses any it can't prove stays inside the worktree — `git -C <shared checkout>` ("redirects git to the shared checkout via -C"), `cd <shared checkout> && git …`, and **any command naming `git` more than once** ("too complex to verify … break it into plain, separate commands"), plus globs, `--bare`, `GIT_DIR`/`env -C` injection and runtime-computed `-C` targets. Version correlation is the proof: ~0 activations across 2.1.201–2.1.221 (2 of 249 on 2.1.220, a gradual rollout), then 6 of 10 sessions on 2.1.222. The strings are in the 2.1.220/221 binaries but the feature is off there, and **there is no config toggle**. This is fatal to the old `skills/merge.md`, whose whole design was "from the worktree, drive the main checkout via `git -C <main_path>`" — it broke at step 1 (the compound state block *and* `git -C "$main_path" branch --show-current`) and step 7 (`git -C <merge_dir> merge`). Splitting commands only clears the "too complex" class; **no Bash rewrite can reach the shared checkout**. The guard applies to the agent's Bash tool, not to the daemon, so the merge moved server-side into the `merge_worktree` MCP tool (`mods/deepsteve-core/merge-worktree.js`, pure logic with an injected git runner; `runGit` in `tools.js` uses `execFileSync('git', argv)` — no shell, so no quoting concerns, no `zsh -l` PATH dependency, and it works on the zsh-less CI unit runner). Merge semantics are unchanged: the same target/merge-dir resolution, the same refuse-on-dirty-target guard, and `--abort` on conflict so the target is left untouched — only `merged` is a success, every other status returns `isError`. **Don't "fix" an agent's guard refusal by having it `git push origin <branch>:main`** — that's the workaround agents improvise, and it moves the remote while leaving the local checkout behind (it left `suburbanmagic` local `main` a commit behind `origin/main`). Note the dirty-target guard assumes the repo gitignores `.claude/` (deepsteve's `.gitignore` has `.claude/*`); a repo that tracks it sees the worktrees dir as untracked and every merge is refused. Tests: `test/unit/merge-worktree.test.js`.
- **Session self-discovery**: Agents can call the `get_my_session_id` MCP tool (no parameters) to get their 8-char shell ID without needing Bash permissions. The shell ID is embedded in the MCP URL via `--mcp-config` at spawn time. Each PTY also gets env vars at spawn: `DEEPSTEVE_SESSION_ID` (8-char shell ID), `DEEPSTEVE_TAB_NAME` (initial tab name), `DEEPSTEVE_WORKTREE` (worktree **name** or empty), `DEEPSTEVE_CWD` (the agent's actual working directory — the `.claude/worktrees/<name>` path for worktree sessions, otherwise the session cwd), `DEEPSTEVE_WINDOW_ID` (browser window ID or empty), and `DEEPSTEVE_API_URL` (e.g. `http://localhost:3000`), and `DEEPSTEVE_API_TOKEN` (bearer token for REST calls to that URL, #536). For live metadata (e.g. after a tab rename), use `get_session_info` MCP tool or `GET $DEEPSTEVE_API_URL/api/shells/$DEEPSTEVE_SESSION_ID/info` (REST endpoints now require `-H "Authorization: Bearer $DEEPSTEVE_API_TOKEN"`) — both return `cwd` (actual working directory, i.e. the worktree path for worktree sessions), `repoRoot` (the main repo checkout), `worktree` (the worktree name or null), and `runningCommand` (for a plain `terminal` session, the command running in its foreground right now, or null when idle at the prompt — computed on demand from the shell's tty foreground process group via `getForegroundCommand()`; always null for agent sessions). **Worktree gotcha:** for Claude (which has native `--worktree` support), the PTY is spawned in the main repo and Claude Code itself moves into `.claude/worktrees/<name>`; `entry.cwd` therefore holds the main repo path, so `cwd`/`DEEPSTEVE_CWD` are resolved to the worktree subdir via `sessionPaths()` rather than reported raw.
- **Session self-close**: The `close_session` MCP tool closes a session from within Claude. The MCP response is sent synchronously before the PTY teardown begins (`killShell` uses `setTimeout` for escalation), so Claude always receives the acknowledgment. A session can close itself or any other session.
- **Meta Controls (`meta_type`, #519)**: The `meta_type` MCP tool (in `deepsteve-core`) lets an agent type into its own or another session's PTY — a **server-side write**, so it works regardless of browser tab focus. Params: `text`, `keys` (control keys sent before text: `Escape`, `Enter`, arrows, `C-c`… — one engine-write each with 250ms gaps, since Ink needs separate stdin reads), `clear_first` (ONE Escape to clear staged composer text — deliberately not two; double-Esc opens Claude Code's history menu), `wait_for_idle` (poll up to 30s for the BEL classifier's idle before typing), `session_id` (defaults to caller), `submit` (default `true`; builds on `submitToShell()` — text then `\r` after 1s for Ink; `submit:false` stages via `engine.write`). The return is **truthful**: `state_before` (`idle`/`busy`/`unknown` via `sessionInputState()`), `landed` (readback heuristic — the ANSI-stripped scrollback tail must contain the typed text), and `screen_tail`. Self-typing enables recursive/self-driving loops, so it is gated behind the `metaControlsEnabled` setting (default **off**) — but instead of failing, a call while disabled triggers an **in-browser consent dialog** (`requestMetaControlsConsent()` in server.js, modeled on the restart confirm: `confirm-meta-controls` over the reload WS, decision via `POST /api/meta-controls-consent`, first response wins, all windows dismissed via `confirm-meta-controls-resolved`). Approval flips the persistent setting; decline starts a 60s cooldown against modal-nagging; **zero connected browsers never auto-confirms**. The handler reads `settings.metaControlsEnabled` live; the tool is always registered (like all mod tools).
- **`read_session_screen` MCP tool**: ungated read-only companion to `meta_type` — returns the last N lines (default 40, max 200) of a session's server-side interpreted terminal buffer plus `state` (`idle`/`busy`/`unknown`) and `seconds_since_output`. Cursor movement, erase operations, alternate-screen redraws, reflow, and CSI intermediate bytes are resolved before lines are returned. Use it to check what a session is doing or to verify typed input landed — no more `browser_eval` poking at `window.__deepsteve` internals.
- **`/rc` inheritance covers server-side spawns (#519)**: `maybeInheritRemoteControl` fires not only from the browser WS new-tab/fork path but also from `start_issue` and `open_terminal` (via the MCP context), with the caller as parent. Prompts are sequenced by a per-shell FIFO inside `deliverPromptWhenReady` (`e.promptQueue`) — the inherited `/rc` submits first, then the issue/initial prompt waits for the next idle; the loading banner and `prompt-submitted` fire only after the **last** queued prompt lands (since #607, only after that prompt has been *verified*, not merely written). Never arm `e.pendingDelivery` directly for prompt delivery — queue through `deliverPromptWhenReady`.
- **`POST /api/settings` reports pruning**: `applySettingsFromBody` returns warnings (invalid fields, `itemEnum` array items dropped — e.g. a stale agent id in `enabledAgents`), which the POST response includes as a `warnings` array (only when non-empty). The settings modal preserves `enabledAgents` entries that have no rendered checkbox (e.g. `hermes`) instead of rebuilding the list from the three rendered ones.
- **HTTPS support**: Opt-in via `--https` flag or `DEEPSTEVE_HTTPS=1`. Runs a second server on port 3443 (configurable via `--https-port` or `DEEPSTEVE_HTTPS_PORT`). HTTP and HTTPS run simultaneously — HTTP for localhost, HTTPS for LAN/Quest. Certs auto-generated at startup using `mkcert` (if available) or `selfsigned` package. Certs regenerate when LAN IPs change. MCP stays HTTP-only (localhost, avoids self-signed cert issues with SDK).
- **Display tabs take `file_path`, not just inline HTML (#599)**: `create_display_tab` / `update_display_tab` accept **exactly one** of `html` or `file_path` (both or neither → `isError`). `file_path` must be absolute (a leading `~/` is expanded), ≤5MB, and is read **once, as a snapshot** — the HTML is copied into `~/.deepsteve/display-tabs/<id>.html` exactly as an inline string would be, so later edits to the source file need another `update_display_tab`. Prefer it whenever the page already exists on disk: the model emits ~15 tokens instead of the whole document. An optional `replacements` map (`{"%%CHANNEL%%": "slot-ab3f9c12"}`) is applied server-side as **literal** find→replace (split/join, longest key first — `$&` in a value stays literal), so a file on disk can stay a reusable template. Display tabs are served same-origin (`GET /api/display-tab/:id`), so pages call back into deepsteve via `window.location.origin` or a relative `/api/...` URL — **never** a hard-coded port, and no port substitution is needed. Shared resolver: `resolveHtml()` in **`html-source.js`** (lifted to the repo root by #618 so Project Mods can use it too — root `*.js` files ship automatically); tests in `test/unit/display-tab-source.test.js`.
- **Browser Console / Screenshots MCP tools**: These operate on the deepsteve UI tab only — they do NOT access your project's website or any other browser tab. `screenshot_capture` and `scene_snapshot` save PNGs to disk and return the file path; use the `Read` tool on that path to view the image. Do NOT try to base64-decode or re-save — the bytes are already on disk at the returned path.
- **Recursive windows (Baby Browser)**: Opening DeepSteve inside its own Baby Browser proxy shares the same origin, so sessionStorage/localStorage/BroadcastChannel would collide. `storage-namespace.js` detects iframe nesting depth and prefixes all keys with `ds{depth}-` (e.g., `ds1-deepsteve`). Depth 0 (top-level) uses no prefix for backward compatibility. Each recursion level gets fully isolated sessions, tabs, and layout state.
- **Pi agent (`@mariozechner/pi-coding-agent`)**: Each pi tab is spawned with `--session-dir ~/.deepsteve/pi-sessions/<shellId>/`, so resume is always `pi --session-dir <same-dir> -c` — no UUID tracking needed. Shutdown uses SIGTERM (pi's graceful signal); Ctrl+C only cancels the current turn. Pi has no MCP support by design, so deepsteve MCP tools (`send_message`, `close_session`, etc.) are not wired into pi sessions — `DEEPSTEVE_*` env vars still propagate, reachable via pi's `bash` tool if needed.
